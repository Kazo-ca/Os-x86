# Essai E14 — DOS et console dans le terminal

Date : 2026-11-11. Code jetable dans `essais/e14-dos-terminal/` (ligne E14 de la section 4.2 du plan du 2026-11-11 ; ADR 9 et 10 ; rangées 109/154, 111, 119, 162, 164 et D27 du registre). L'essai simule le terminal de Kazo dans une page (écran plein à largeur fixe, jeu de touches réduit d'une commande Terminal) et y affiche trois choses : FreeDOS 1.4 par l'écran texte VGA de v86 ; `wine cmd` et un `.exe` console compilé pour l'occasion, par la console VGA de Linux (tty1) puis par un pty relié à un port série ; un shell `bash`. Il mesure la latence « touche → écran » et « écriture dans l'invité → écran » à quatre fréquences de sondage, ce qui manque sans F1-F12 ni Alt, la détection du passage en mode graphique, le code de sortie, Ctrl+C, le redimensionnement, et le coût CPU/mémoire.

Non couverts : le vrai Terminal de Kazo (simulé), QBASIC (absent de FreeDOS), Firefox/Edge/Safari, le Web Worker, le mode brut (D27, V2), un vrai pty Kazo.

## But

Savoir si un programme DOS texte et `cmd` de Wine sont utilisables dans l'onglet du terminal de Kazo avec `get_text_screen` et le jeu de touches d'une commande Terminal (critère : latence < 100 ms par rafraîchissement), quelle voie choisir pour un programme console Wine (162, 154 B), ce qu'il faut demander au Terminal de Kazo dans l'ADR 10, et quel signal déclenche « DOS graphique → BoxedWine » (164 A).

## Ce qui a été construit

Tout est dans `essais/e14-dos-terminal/` (README de 10 lignes).

- `terminal.html` + `terminal.js` : **simulateur du terminal de Kazo**. Une grille texte (`<div>` par ligne, `<span>` par suite de cellules de même couleur, 80x25, redimensionnable) et un curseur. Deux voies d'alimentation : **VGA**, par sondage (16, 33, 50 ou 100 ms) de l'écran texte de v86 — soit `screen_adapter.get_text_screen()` de l'adaptateur « ansi » de v86 (`screen: { ansi: true }`, sans canvas ni conteneur DOM ; chaque ligne arrive avec des SGR 24 bits), soit une lecture brute de la mémoire texte du périphérique VGA (`emu.v86.cpu.devices.vga.vga_memory`, code CP437 + attribut, API interne) ; **pty**, par les octets de ttyS1 (`serial1-output-byte`) interprétés par un petit émulateur VT (xterm réduit : CR/LF, retour arrière, CUP/CUU/CUD/CUF/CUB, ED/EL, IL/DL/ICH/DCH/ECH, région de défilement, écran alternatif, SGR 16 couleurs, DSR/DA). Entrée clavier filtrée comme pour une commande Terminal de Kazo : lettres, chiffres, ponctuation, Entrée, Retour, Tab, flèches, Échap, Ctrl+lettre ; **F1-F12 et Alt refusés** ; Ctrl+C réservé (« Kazo ferme la commande ») ou transmis ; Home/End/Suppr/Page refusés en mode strict. Voie VGA : scancodes PS/2 (set 1, Shift pour les majuscules, E0 pour les flèches) par `keyboard_send_scancodes` ; voie pty : octets et séquences xterm par `serial_send_bytes(1, …)`. Option `?chord=1` : **Échap puis lettre = Alt+lettre, Échap puis chiffre = F1-F12** (ce qu'un Terminal pourrait traduire lui-même). Mesures : à chaque touche, un guetteur hors sondage note l'instant où l'écran de v86 (ou l'écho de ttyS1) change (`change_ms`), et le sondage note l'instant du rendu DOM (`render_ms`) ; coût par tour de sondage (lecture, total, max, lignes changées, retards) ; événement `screen-set-size` (bpp ≠ 0 = mode graphique).
- `server.mjs` (COOP/COEP, Range, dépôt d'état), `drive.mjs` (pilotage à la main : touches, commandes sur ttyS0, écran, statistiques, CPU, mémoire, captures), `run.mjs` (mesure automatique, trois runs par invité).
- **DOS** : `download-freedos.ps1` (FreeDOS 1.4 LiteUSB 17 Mio et LiveCD 280 Mio, SHA-256 vérifiés contre `verify.txt` de freedos.org) ; `make-dos-image.py` + `Dockerfile.mtools` (image Docker `e14-mtools`, mtools) : `images/dos.img` = FD14LITE.img (32 Mio, FAT16) avec un `FDAUTO.BAT` sans installateur (`FDAPM APMDOS` pour l'oisiveté), `\E14\` : `KEYTEST.COM` (affiche scancode/ASCII de chaque touche, Échap rend le code 7), `GUESS.COM` (jeu texte : deviner un chiffre), `GFX.COM` (mode 13h puis retour au mode 3), tous trois assemblés à la main dans le script Python, plus `CHOICE`, `DEBUG`, `FIND` des paquets BASE et un fichier texte de 120 lignes. v86 : `hda` = `dos.img` (chargé en mémoire), 64 Mio.
- **Console Wine** : `Dockerfile` = recette E17 (Debian trixie i386 + `winehq-stable` 11.0 + noyau `linux-virt` d'Alpine) **plus** `wine-stable-dev` (winegcc), `gcc-mingw-w64-i686`, `socat`, `kbd`, `nano`, `less`, `vim-tiny`, `ncurses-term` ; `guest/consoletest.c` compilé en **PE i386** (`winegcc -b i686-w64-mingw32 -mconsole`) : lit stdin ligne par ligne, écrit stdout, `color` essaie `SetConsoleTextAttribute`, `exit N` rend le code N, `--loop` tourne sans fin (test de Ctrl+C). `guest/init.sh` **ne charge pas le pilote DRM `bochs`** (contrairement à E17) : tty1 reste en mode texte VGA (`vgacon`), donc lisible par `get_text_screen` ; `atkbd` chargé pour le clavier. `guest/vga-run.sh` : lance un programme avec tty1 pour stdin/stdout/stderr (`TERM=linux`) et écrit `E14-EXIT <code>` sur tty1 et ttyS0 à la fin. `guest/pty-run.sh` : lance un programme sous `script -q -e` (pty util-linux), ttyS1 en mode brut sans écho des deux côtés, `TERM=xterm`, taille `stty rows/cols` choisie au lancement, et écrit `E14-EXIT <code>` sur ttyS1 à la fin (le lanceur de 110). Image : `build.ps1` → Docker `e14-wine-console`, `images/wine-fs.json` + `images/rootfs-flat/`. v86 : racine 9p, 1024 Mio, `console=ttyS0`.

## Protocole

`run.mjs --guest dos` (trois runs, contexte Chrome neuf à chaque run) : boot jusqu'à `E14 READY` ; pour chaque fréquence de sondage 16, 33, 50, 100 ms : frappe mesurée d'une ligne de 34 touches au prompt (latence par touche), `dir /s \packages` (défilement de ~250 lignes : tours de sondage, lignes changées, retards, durée), CPU du renderer pendant six `dir /s` enchaînés puis à l'oisiveté ; puis lecture `get_text_screen` de l'adaptateur ansi contre lecture brute (coût par tour) ; `KEYTEST` avec les touches du jeu Kazo et les accords Échap+f, Échap+1, Échap+0 ; code de sortie 7 relu par `%errorlevel%` ; `GFX` (délai entre Entrée et l'événement mode graphique, retour au texte) ; `CHOICE` ; `GUESS` ; `EDIT` (Ctrl+N, frappe, flèches, capture, menu par accord) ; mémoire.

`run.mjs --guest wine` (trois runs) : boot jusqu'au prompt série ; **voie (a)** tty1 : `echo` + `stty size`, latence « écriture dans l'invité → écran » (commande sur ttyS0 qui écrit sur tty1, cinq fois), `wine cmd` (temps de démarrage, latence par touche aux quatre fréquences, `ver`, `dir`, `color`, capture), `consoletest.exe` dans `cmd` (lignes, `color`, `exit 5`, `%errorlevel%`), sortie de `cmd` et code relu, `consoletest.exe --loop` lancé directement puis Ctrl+C transmis (code attendu 130) ; **voie (b)** ttyS1 : les mêmes étapes, plus un lancement en 100x30 (`stty size`, ligne de 100 caractères) ; **shell** `bash -i` par (b) : `ls --color`, `less` (défilement, recherche), `nano` (frappe, Ctrl+O, Ctrl+X, relecture), `vi` (`G`, `o`, Échap, `:wq`), séquences VT inconnues rencontrées ; CPU à l'oisiveté par voie ; mémoire.

Chrome installé piloté par Playwright, headless (pas de session visible : voir Limites) ; captures `images/e14-*.png` du seul élément terminal.

## Résultats

Temps en millisecondes sauf mention. « change » = délai entre l'envoi de la touche (ou de la commande) et le changement de l'écran texte de v86 (ou l'écho sur ttyS1), mesuré par un guetteur hors sondage (résolution ~1 à 4 ms) ; « rendu » = délai jusqu'à la mise à jour du DOM par le sondage. Trois runs ; médiane, 90e centile et maximum sur les 30 touches visibles d'une ligne (les 4 espaces ne changent pas le texte et sont exclus).

### DOS (FreeDOS 1.4 dans v86, voie VGA, lecture brute de la mémoire texte)

Boot jusqu'à l'invite : **2,6 à 2,8 s** (image de 32 Mio chargée entière, 64 Mio de RAM). `DIR`, `TYPE`, `CHOICE` (rc 2 pour N), `GUESS` (gagné), `KEYTEST`, `EDIT` : tout se lit et se pilote depuis la grille du terminal (captures `images/e14-dos-run<n>-edit.png`, `e14-dos-headed-*.png` : couleurs, cadres, ombrage et curseur fidèles à 80x25).

| Sondage | Touche → change (méd. / p90 / max) | Touche → rendu (méd. / p90 / max) | `dir /s` : durée, tours, rendus, lignes changées, coût par tour (moy. / max), retards | CPU renderer en défilement | CPU renderer à l'oisiveté |
|---|---|---|---|---|---|
| 16 ms | 37 à 48 / 63 à 65 / 64 à 67 | 49 à 51 / 68 à 70 / 72 à 76 | 1,6 à 1,7 s ; 102 à 110 tours ; 67 à 68 rendus ; 1 279 à 1 304 lignes ; 0,21 à 0,24 ms / 0,5 à 1,2 ms ; 0 retard | 64 à 75 % | 2,3 % |
| 33 ms | 30 à 34 / 50 à 65 / 62 à 66 | 47 à 54 / 69 à 72 / 71 à 94 | 1,4 à 1,5 s ; 42 à 44 tours ; 34 à 35 rendus ; 501 à 537 lignes ; 0,21 à 0,26 / 0,3 à 0,5 ; 0 | 64 à 74 % | 0,9 à 4,1 % |
| 50 ms | 15 à 25 / 50 à 63 / 64 à 66 | 34 à 47 / 80 à 103 / 97 à 107 | 1,3 à 1,4 s ; 25 à 27 tours ; 24 à 26 rendus ; 330 à 348 lignes ; 0,24 à 0,25 / 0,4 ; 0 | 59 à 61 % | 0,9 à 1,7 % |
| 100 ms | 0,6 à 9 / 51 à 62 / 62 à 66 | 82 à 88 / 94 à 100 / 97 à 107 | 1,3 à 1,4 s ; 13 à 14 tours ; 13 à 14 rendus ; 174 à 203 lignes ; 0,25 à 0,31 / 0,3 à 0,6 ; 0 | 61 à 66 % | 0,3 à 2,3 % |

Lecture : le **coût d'un tour de sondage est négligeable** (0,2 à 0,3 ms pour lire 80x25 cellules avec attributs, comparer et réécrire les lignes changées ; `get_text_screen()` de l'adaptateur ansi de v86 : 0,04 ms de lecture, 0,24 à 0,28 ms au total, pareil). Le CPU en défilement (60 à 75 %) est celui de v86 qui exécute `DIR`, pas du sondage : à l'oisiveté, 16 ms de sondage coûtent ~2 % et 100 ms ~0,5 %. Le rendu DOM d'un tour qui change des lignes reste sous 1,3 ms.

**La latence « touche → change » ne vient ni de la page ni du sondage, mais de l'oisiveté de FreeDOS** : avec `FDAPM APMDOS` (HLT quand DOS attend une touche), v86 ne réveille pas le CPU arrêté à l'arrivée d'un scancode mais au prochain tic du PIT (18,2 Hz, 55 ms), d'où une latence uniforme entre 0 et ~65 ms (médiane 30 ms à 33 ms de sondage). Contrôle manuel au même réglage de sondage : `FDAPM APMOFF` (DOS boucle) → **touche → change 4,3 ms (p90 4,8, max 4,9), touche → rendu 14 ms (p90 35, max 40)**, mais renderer à **100 %** d'un cœur ; `FDAPM APMDOS` → 28 / 61 / 67 et 50 / 68 / 95, renderer à **0,7 %**. (Le mélange des deux chiffres explique aussi pourquoi la médiane « change » baisse quand le sondage ralentit : moins de tours = v86 plus souvent dans son tic = l'échantillon tombe plus souvent juste après le réveil.) Pour un DOS oisif le rafraîchissement complet touche → écran tient donc dans **~50 ms en médiane et < 100 ms au p90 à 16 ou 33 ms de sondage** ; à 50 ms il dépasse 100 ms au p90 et à 100 ms en médiane.

**Jeu de touches** (`KEYTEST`, int 16h, scancode/ASCII en hexadécimal) : `a` → `1E/61`, `A` → `1E/41` (Shift simulé), `!` → `02/21`, `\` → `2B/5C`, ↑ → `48/00`, ← → `4B/00`, Tab → `0F/09`, Retour → `0E/08`, Ctrl+A → `1E/01`, Entrée → `1C/0D`, Échap → `01/1B` ; tout le jeu de Kazo passe. Code de sortie du programme relu par `%errorlevel%` (7). Accords (traduits par le simulateur, hors jeu de Kazo) : Échap+f → `21/00` (Alt+F), Échap+1 → `3B/00` (F1), Échap+0 → `44/00` (F10).

**EDIT 0.9a sans F1-F12 ni Alt** : le programme s'ouvre sans document ; la barre de menus ne s'atteint que par Alt+lettre ou F10, et l'aide par F1 : **avec le jeu strict de Kazo, on ne peut ni ouvrir un fichier, ni sauver, ni quitter par le menu**. Contournements trouvés : EDIT a des raccourcis Ctrl dans le jeu de Kazo (**Ctrl+N** nouveau, **Ctrl+O** ouvrir, **Ctrl+S** sauver : la boîte « Save As » s'ouvre et se parcourt par Tab, flèches et Entrée) ; `edit fichier.txt` ouvre directement le document ; Quitter n'a pas de raccourci Ctrl → il faut l'accord Alt. Avec l'accord Échap+f, le menu Fichier s'ouvre **si Alt est tenu** : envoyé en une seule rafale (Alt↓ F↓ F↑ Alt↑), EDIT avec un document ouvert l'ignore ; avec ~40 ms entre l'appui d'Alt, la touche et le relâchement, le menu s'ouvre, puis `x` (Exit) et `n` (ne pas sauver) rendent l'invite (`run.mjs`, qui envoyait la rafale, note `menu_opened_by_chord: false` ; le contrôle manuel avec Alt tenu l'ouvre à chaque fois). Pas de QBASIC dans FreeDOS 1.4 (non mesuré).

**Signal « DOS graphique »** (`GFX.COM`, mode 13h) : v86 émet `screen-set-size` avec `bpp` ≠ 0 (`[320, 25, 8]` puis `[320, 200, 8]`) **63 à 109 ms après Entrée** ; retour au texte : `[80, 25, 0]`. Pendant le mode graphique `get_text_screen()` ne devient pas vide : il garde le dernier écran texte (25 lignes figées). Au boot, le BIOS passe par `[80, 256, 0]`, `[80, 16, 0]` puis `[80, 25, 0]` : la grille doit suivre la taille texte courante, pas seulement le drapeau graphique.

**Mémoire** (DOS, 64 Mio) : tas JS 12 à 21 Mio ; renderer 254 à 265 Mio privés ; tous les processus Chrome 462 à 475 Mio.

### Console Wine : voie (a) tty1 (console VGA de Linux) contre voie (b) pty sur ttyS1

Boot Debian jusqu'au prompt série : **43 à 51 s** (1024 Mio, racine 9p à la demande) ; tty1 reste en mode texte (pas de DRM). Trois runs valides par voie (runs 4, 5, 7 ; les runs 1 à 3 avaient des bogues de harnais, voir plus bas). `wine cmd` atteint son invite **44 à 74 s** après la commande (premier processus Wine de la VM, 9p froid, comme E17) ; le `consoletest.exe` lancé ensuite dans `cmd` démarre en quelques secondes.

Lecture : la latence de la page est la même dans les deux voies (le sondage domine : rendu ≈ change + sondage/2) ; la différence est dans l'invité : Wine répond en **3 ms** sur tty1 et **4 ms** sur le pty. **Les deux voies tiennent le critère (< 100 ms) à 16, 33 et 50 ms de sondage** (p90 ≤ 59 ms) ; à 100 ms, le p90 dépasse 94 ms et le maximum 100 ms.

Ce que `cmd` affiche mal (les deux voies) : la ligne vide supplémentaire après chaque sortie ; `color` repeint tout l'écran (bien rendu) ; aucune frappe anticipée pendant qu'une commande s'exécute (conhost repasse le tty en brut avec purge de l'entrée : les touches tapées pendant `color 1e` ont été perdues en essai manuel) ; `XDG_RUNTIME_DIR` absent → avertissement au premier lancement (corrigé par l'environnement du lanceur).

### Shell Linux (119, 195) par la voie (b)

`bash -i` dans le pty (TERM=xterm, 80x25) : prompt en moins d'une seconde ; `ls --color` : **115 cellules colorées**, touche → change 2,2 à 2,8 ms (p90 2,8 à 3,3), → rendu 24 à 27 ms (p90 31 à 33) à 33 ms de sondage ; `less` (fichier existant) : défilement par flèches et espace (change 3 à 9 ms), recherche `/motif`, `q` ; `nano` : interface en 0,6 s, frappe, **Ctrl+O, Entrée, Ctrl+X** sauvent (fichier relu) ; `vi` : `G`, `o`, frappe, Échap, `:wq` sauvent (fichier relu) ; `exit` → code 0 relu. Capture `images/e14-wine-bash-nano.png`, `e14-wine-run4-bash-ls.png`. Ce qui manque avec le jeu de Kazo : les raccourcis **Alt** de nano (M-D, M-A, M-B… affichés dans sa barre), les **F-touches** (`mc`, `htop`), le **redimensionnement** à chaud (la taille est celle du lancement ; un SIGWINCH demanderait un canal de contrôle), Home/End/Suppr/Page en mode strict (réglables : le simulateur les refuse par choix), et Ctrl+C si Kazo le garde pour fermer la commande. Séquences VT inconnues rencontrées : aucune après l'ajout de REP.

### Coût (page seule, hors v86)

Par tour de sondage (80x25) : lecture 0,03 à 0,04 ms, total 0,2 à 0,3 ms sans changement, ≤ 1,3 ms avec changement (DOM). CPU du renderer à l'oisiveté de l'invité : 0,3 à 2,3 % (DOS, selon la fréquence), 3 à 4 % (Debian, dont le noyau) ; en défilement DOS 60 à 75 % (c'est v86). **Fréquences utiles** : 33 ms (30 Hz) suffit (rendu médian ~20 ms, p90 ~30 ms) ; 16 ms gagne 10 ms de médiane pour ~1,5 % de CPU en plus ; 100 ms rate le critère. Un rafraîchissement n'est utile que s'il y a changement : 35 rendus pour 44 tours en défilement à 33 ms, 13 à 14 sur 14 à 100 ms, et ~0 à l'oisiveté grâce à la comparaison.

**Glyphes** : la lecture brute de la mémoire VGA avec une table CP437 maison et l'adaptateur ansi de v86 donnent les mêmes caractères (vérifié sur la ligne de titre d'EDIT : 0xBF → U+2510 « ┐ » dans les deux ; aucune paire de substitution orpheline) ; cadres, ombrage et flèches d'EDIT se rendent. Le curseur n'est pas exposé par l'API publique de v86 (ni par `get_text_screen`) : lu dans `vga.cursor_address` (interne).

## Ce qui a raté ou a été contourné

- **Deuxième UART absent** : v86 ne crée `uart1` (ttyS1, 0x2F8) que si l'option non documentée `uart1: true` est passée ; sans elle, le noyau voit `uart:unknown` et `open()` rend EIO. Idem `uart2`/`uart3`.
- **`open()` de ttyS1 qui bloque** : sans porteuse DCD (v86 ne la lève pas), un `open()` ordinaire attend ; `stty -F` (O_NONBLOCK) passe. Contourné par `clocal` avant `socat`, et la page lève DCD/DSR/CTS (`serial_set_carrier_detect(1, true)`) au démarrage.
- **util-linux `script` abandonné** pour la voie (b) : il copie les attributs de son stdin dans le pty (ligne brute héritée), repasse stdin en brut avec purge (`TCSAFLUSH` : premiers octets de sortie perdus) et ne transmettait pas la taille. Remplacé par `socat FILE:/dev/ttyS1,raw,echo=0 EXEC:…,pty,setsid,ctty` + un lanceur dans le pty (`pty-child.sh`) qui fixe la taille, lance, puis écrit le code.
- **SIGINT tue aussi le lanceur** dans le pty (toute la session au premier plan) : `trap ":" INT` dans `pty-child.sh` (un gestionnaire, pas SIG_IGN que le programme hériterait).
- **Chemins Windows dans la ligne de commande** : `z:\root\x.exe` passé par le shell série puis `socat` perd ses barres obliques ; les scripts utilisent le chemin Unix (`wine /root/consoletest.exe`).
- **`cache=loose` (9p)** : un fichier injecté sous un nom existant garde son ancien contenu côté invité ; un dossier créé puis rempli depuis l'hôte peut être listé vide quelques secondes. `run.mjs` injecte sous `/root/e14/` et attend que les quatre fichiers soient listés. Trois runs sur neuf ont pourtant eu une voie pty muette dès le premier programme (runs 1 et 2 : l'image ne contenait pas encore `pty-child.sh`, chemin absolu ; run 10 : cause non trouvée, reproduction manuelle impossible) ; les chiffres pty viennent des runs 4, 5 et 7 et des contrôles manuels.
- **Enchaînement de deux pty sur le même port série** : dans `run.mjs`, le programme suivant est lancé ~100 ms après la sortie du précédent ; le `socat` précédent tient encore ttyS1 (Wine libère son pty avec retard) et les deux lanceurs se partagent le port : Ctrl+C et redimensionnement automatisés ont échoué dans tous les lots (sortie muette ou mêlée), alors que les mêmes commandes espacées de quelques secondes réussissent à la main (code 58 après Ctrl+C, `stty size` = `30 100`). Pour Os-x86 : un canal par programme console (pty via l'agent), jamais un port série partagé.
- **Harnais** : `E14-EXIT` sur ttyS0 précédé du prompt du shell (ancre `^` retirée) ; baseline des événements « exit » prise avant le lancement (le code arrive avant l'attente) ; `$` d'une regex contre des lignes à espaces de fin ; `/etc/services` absent de trixie-slim (`less` testé à la main sur `/etc/bash.bashrc`) ; `nano` attendu par « GNU nano » plutôt qu'un délai fixe. Le run DOS 1 a été refait ; les runs Wine 1 à 3 sont gardés comme traces mais exclus des tableaux.
- **Accord Alt** : envoyé en une rafale, EDIT (document ouvert) l'ignore ; Alt tenu ~40 ms entre les scancodes → marche. `run.mjs` mesurait la rafale (`menu_opened_by_chord: false`), la correction est dans `terminal.js`, revérifiée à la main.
- **Chrome visible** : une session headed (fenêtre réelle) a servi à une capture DOS (`e14-dos-headed-*.png`) ; les autres captures sont headless (même renderer, mêmes pixels).

## Limites

- Terminal de Kazo **simulé** (grille HTML, jeu de touches filtré) : le vrai `IFullScreenTerminalSession` (rendu, focus, flux UTF-16) n'a pas été utilisé ; v86 tourne sur le fil principal de la page, pas dans un worker (ce qui changera la mesure « change », pas le sondage).
- Un seul invité à la fois par page ; pas de save/restore d'état ; Chrome seulement ; une machine rapide (Ryzen 3700X).
- Trois à quatre instances de v86 ont parfois tourné en même temps (E7 et des lots E14 superposés) : bruit possible sur les maxima, pas sur les médianes (identiques entre lots).
- `cmd` et `consoletest.exe` seulement comme programmes console Windows ; pas de programme « plein écran » Windows (`edit.com` de Windows, `far`), pas de test de `GetConsoleScreenBufferInfo`/déplacement de curseur sur tty1.
- Mode brut (D27, V2) non traité : le jeu de touches réduit est pris tel quel ; Home/End/Suppr/Page sont refusés par choix du simulateur (Kazo les a peut-être).
- QBASIC absent ; pas de jeu DOS libre dans FreeDOS Lite : `GUESS.COM` maison seulement.

## Chiffres bruts

`essais/e14-dos-terminal/results-dos-{1,2,3}.json` (DOS, runs valides), `results-wine-{4,5,7}.json` (Wine, runs valides ; 1 à 3 : traces avec bogues de harnais ; 10 à 12 : lot corrigé pour Ctrl+C, redimensionnement et shell), captures `images/e14-*.png`, journaux `images/run-*.log`, `images/drive-*.log` (dossier `images/` ignoré par git). ## Ce que ça veut dire pour Os-x86

Tout est « à valider » ; ce sont les conclusions de l'essai, pas des décisions.

1. **Critère E14 : atteint.** Un programme DOS texte (`DIR`, `EDIT`, `CHOICE`, un `.COM` qui lit le clavier, un jeu texte) et `cmd` de Wine (plus un `.exe` console qui lit stdin, écrit stdout et rend un code) sont utilisables dans une grille de terminal alimentée par l'écran texte de v86, avec le jeu de touches d'une commande Terminal de Kazo. **Latence par rafraîchissement : ~20 ms en médiane et ≤ 36 ms au maximum à 33 ms de sondage pour Wine ; ~50 ms en médiane, ≤ 95 ms pour un DOS oisif** (la part DOS vient du réveil de v86 au tic du PIT, pas du terminal). 100 ms de sondage rate le critère ; **33 ms est la fréquence à retenir**, 16 ms n'apporte que 10 ms de mieux.
2. **Voie recommandée pour 162 / 154 B (programme console Wine dans le Terminal) : la voie (b), pty + port série (ou virtio-console) + émulateur VT dans le Terminal**, pas la console VGA. Mêmes latences et même fidélité que (a), mais : plusieurs programmes console en même temps (un pty chacun, tty1 est unique), taille choisie par le Terminal (80x25 ou autre, SIGWINCH possible), **code de sortie écrit par le lanceur sur le même canal** (110), Ctrl+C = un octet 0x03 que le pty transforme en SIGINT (rien à faire côté Kazo, et c'est le même code 58 qu'en (a)), pas de dépendance au mode texte VGA (donc compatible avec une VM qui a Xorg/DRM pour BoxedWine : **la voie (a) est incompatible avec le pilote `bochs` d'E17**, qui fait passer tty1 en framebuffer). Coût : un petit émulateur VT (xterm réduit : ~250 lignes ici, ou xterm.js) dans le Terminal ; c'est l'agent (E7, virtio-console) qui devrait ouvrir le pty et relayer les octets plutôt que ttyS1.
3. **Voie recommandée pour DOS texte (111, 154 B) : la voie VGA** (`get_text_screen` ou lecture de la mémoire texte) : FreeDOS n'a pas de pty. Sondage à 33 ms, comparaison par ligne, rendu des attributs VGA 16 couleurs. Latence acceptable mais pour descendre sous 10 ms il faudrait que v86 réveille le CPU en HLT à l'arrivée d'un scancode (contribution amont possible) ; pas de `FDAPM` = 100 % CPU, à exclure.
4. **Signal 164 A (DOS graphique → BoxedWine)** : l'événement `screen-set-size` de v86 avec `bpp ≠ 0`, émis 60 à 110 ms après le passage en mode graphique ; retour au texte = `bpp 0`. `get_text_screen()` ne se vide pas : ne pas s'y fier. Au boot, la taille texte passe par 80x256 et 80x16 : suivre les changements de taille texte aussi. Reste ouvert : BoxedWine doit pouvoir **reprendre** une VM DOS déjà lancée par le Terminal (même VM, canvas de v86 montré dans une fenêtre), puis la rendre au Terminal au retour en mode texte, ou le Terminal refuse DOS graphique avec un message.
5. **Ce que l'ADR 10 doit demander au Terminal de Kazo** : (i) une surface « écran plein » à largeur fixe (80 colonnes, 25 lignes ou plus) avec **attributs de couleur par cellule** (16 couleurs VGA / ANSI) et un curseur, rafraîchie par remplacement de lignes à ~30 Hz ; (ii) l'entrée touche par touche avec **Ctrl+lettre** (indispensable : Ctrl+N/O/S d'EDIT, Ctrl+O/X de nano, Ctrl+C transmis au programme sinon rien ne l'interrompt) ; (iii) **un accord pour Alt et les F-touches** (Échap puis lettre/chiffre, comme la touche Méta des terminaux), traduit par le Terminal en Alt+lettre/F1-F12 : sans lui, EDIT ne peut pas quitter, QBASIC n'aurait pas de menus, `mc`/`htop` sont infirmes ; l'Alt doit être « tenu » (trois envois espacés) sur la voie VGA ; (iv) décider si **Ctrl+C ferme la commande ou va au programme** (proposition : Ctrl+C au programme, Ctrl+Pause ou un bouton pour tuer) ; (v) Home/End/Suppr/Page si Kazo les a (les éditeurs les attendent) ; (vi) la taille de la surface (colonnes × lignes) connue à l'ouverture, et un événement de redimensionnement en V2.
6. **Shell Linux (119, 195)** : `bash` par la voie (b) est utilisable en V1 tel quel (couleurs, `less`, `nano`, `vi`) ; les touches manquantes acceptées par 119 sont Alt et F-touches (nano, mc), et le redimensionnement à chaud.
7. **Coût** : négligeable côté page (0,3 ms par tour, ~2 % de CPU) ; la mémoire est celle de la VM (DOS 64 Mio → renderer 260 Mio ; Debian 1024 Mio → 1,8 Gio). Un onglet de terminal par VM, pas un v86 par programme console.
8. **v86** : à ajouter dans Os-x86 (ou à proposer en amont) : `uart1: true` documenté ou un virtio-console pour le pty ; accès au curseur et aux attributs par une API publique (aujourd'hui `screen_adapter.get_text_screen()` en ANSI 24 bits via `screen: { ansi: true }`, curseur interne) ; réveil sur IRQ clavier en HLT.
