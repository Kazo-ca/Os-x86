# Étude E10 — navigateurs et mobile (lecture)

Date : 2026-11-10. Étude documentaire, sans code (ligne E10 des études prévues ; nourrit §17 des consignes). Elle croise les fonctions du navigateur que les maquettes E1, E2, E4 et E5 ont réellement utilisées ou prévues (OPFS avec `createSyncAccessHandle()` dans un worker, Web Worker + OffscreenCanvas, AudioWorklet + `MessagePort`, isolation d'origine croisée COOP/COEP, mémoire wasm de 1 Gio, `navigator.storage.persist()`/`estimate()`) et celles que le reste du projet suppose (Pointer Lock, verrouillage du clavier, manette, Web Locks, presse-papiers, WebCodecs, fenêtre détachée, Wake Lock) avec les versions minimales des navigateurs et leurs réserves.

## But

Donner un tableau « fonction × navigateur » avec versions minimales et réserves, dire ce qui change sur mobile (mémoire par onglet, tactile sans clavier, disposition mobile de Kazo), ce qu'une fenêtre détachée (second écran) permet, et ce qui tue ou gèle un worker v86 en arrière-plan ; en sortir une liste de fonctions à marquer « non prises en charge ici » par navigateur.

## Méthode et sources

- Versions minimales prises dans les données brutes de compatibilité de MDN (`browser-compat-data`, fichiers JSON) et de caniuse (fichiers JSON), pas dans les pages rendues (leurs tableaux ne se lisent pas hors navigateur). Quand MDN dit « mirror », la version est celle du navigateur de bureau ou de Chrome Android correspondant ; pour Samsung Internet, la version est déduite de la base Chromium (Samsung 29 = Chromium 136 d'après Wikipédia ; la base des versions 30.x de 2026 n'est pas publiée) et marquée « ≈ ».
- Règles de quota, d'éviction, de gel et de déchargement : pages des éditeurs (Chrome for Developers, WebKit, Mozilla, Microsoft) et intentions blink-dev ; limites mémoire iOS/Android : bugs WebKit et fils Chromium cités, faute de chiffre officiel.
- Versions stables au 2026-11-10 : Chrome 156, Edge 157, Firefox 159 (27 oct. 2026), Safari 27.2 (26 oct. 2026 ; Safari 26.x est donc l'avant-dernière lignée), Samsung Internet 30.0.5 (23 oct. 2026). Sur iOS et iPadOS, tous les navigateurs (Chrome, Firefox, Edge compris) utilisent WebKit : la colonne « Safari iOS » vaut pour eux ; l'exception des moteurs tiers dans l'UE (iOS 17.4+) n'a pas été vérifiée et est ignorée ici.
- Chaque cellule dont je ne suis pas sûr porte un numéro de source [n] ; « non vérifié » = aucune source primaire trouvée dans le temps de l'étude. Rien n'a été exécuté : aucune mesure nouvelle, seulement les chiffres de E1/E2/E5 rappelés quand ils éclairent une ligne.

Lecture de la matrice :

- Les cinq fonctions que les maquettes ont utilisées (lignes 1-4, 11) existent partout depuis 2023 au plus tard, Safari compris. Les écarts sont dans les réserves : OPFS synchrone seulement dans un worker (confirmé par E2 : absent de la page) ; `Atomics.wait` interdit dans le fil principal ; SAB conditionné à l'isolation d'origine croisée ; persistance jamais acquise sans geste.
- Memory64 (ligne 6) est absent de Safari (y compris 27.2) : sans importance tant qu'Os-x86 reste en wasm32 (v86 l'est), mais ça ferme la voie « plus de 4 Gio pour une VM » sur Mac et iOS.
- Pointer Lock et Keyboard Lock (lignes 8-9) sont des fonctions de bureau : Firefox et Safari ont rejoint le verrouillage du clavier en 2026 (151 et 26.4) par la variante `requestFullscreen`, Chrome garde l'API `navigator.keyboard.lock()`. Deux API, un seul besoin : à abstraire.
- La fenêtre détachée (ligne 17) n'a de forme « toujours au-dessus » que dans Chrome/Edge (116) et Firefox (151) ; jamais Safari.

## Mobile

**Mémoire par onglet.**
- iOS/iPadOS : aucune limite publiée ; le processus WebContent est tué par jetsam selon la pression système. Bug WebKit 269777 (iOS 17, appareils de 4 à 6 Go) : ~1 Gio allouable à la première visite, **300-500 Mio après rechargement**, 28 Mio sur un iPhone Xs ; dupliqué vers le « MegaBug » 269937 (fragmentation Gigacage/SAB), toujours ouvert [31]. Bug 221530 : `memory.grow()` n'échoue pas, Safari recharge l'onglet sans prévenir [32]. Bug 256703 : jetsam `per_process_limit` au-dessus de 1,4 Go [33]. Rappel E1 : le renderer Chrome pèse 1,4 Gio dès le boot pour `memory_size` = 1 Gio, 3,3 Gio avec l'état en mémoire. **Une VM de 1 Gio n'est pas tenable sur iOS ; 256 Mio (configuration de E5, état de 78 Mo) est la seule configuration plausible, et encore non vérifiée.**
- Android : Chrome n'est en 64 bits que sur Android 10+ avec ≥ 8 Go de RAM (seuil ~6,5 Go vus du noyau) [36] ; en 32 bits, la mémoire wasm plafonne en pratique vers 256-700 Mio par fragmentation d'adresses [37][38]. Les onglets en arrière-plan sont gelés après 5 min et tués en priorité sous pression [28][42]. Samsung Internet : mêmes bases Chromium, pas de chiffre propre (non vérifié).

**Tactile, sans clavier physique.**
- Pointer Lock : absent sur iOS ; sur Android, l'intention Chrome 144 suppose une souris physique [11]. Sans Pointer Lock, pas de capture relative de la souris : un programme Windows qui attend des mouvements relatifs (jeux, CAO) n'est pas pilotable au doigt.
- Keyboard Lock : sans objet. Le clavier virtuel ne produit que du texte (pas de touches système, de F-touches ni de combinaisons Ctrl/Alt fiables) : l'invité a besoin d'un clavier à l'écran fourni par Kazo (Échap, Tab, F1-F12, Ctrl, Alt, Win, flèches).
- Clavier virtuel et viewport : son apparition réduit la zone visible ; l'écran VGA de 1024×768 de E1/E4 ne tient pas sur un téléphone sans mise à l'échelle ; les clics « précis » de Win32 (boutons de 16 px) demandent un zoom ou un curseur déporté (pavé tactile virtuel).
- Son : la lecture démarre seulement après un geste (`AudioContext.resume()`, E5) ; sur iOS le blocage est plus strict qu'en bureau (non vérifié par E5, qui n'a vu que Chrome).
- Wake Lock : disponible partout sur mobile (ligne 19) ; sans lui, l'écran s'éteint et l'onglet passe en arrière-plan → gel ou mort de la VM (section suivante).

**Ce que la disposition mobile de Kazo implique pour une fenêtre de VM.** Petit viewport, une fenêtre à la fois, pas de fenêtre détachée (Doc-PiP absent sur mobile), pas de second écran, pas de Pointer Lock ni de Keyboard Lock, mémoire d'un tiers à un dixième du bureau, mort du processus dès que l'onglet quitte l'avant-plan. Autrement dit, la disposition mobile ne peut offrir qu'une vue plein écran d'une petite VM, en avant-plan, avec clavier et pavé tactile virtuels, et doit considérer que la VM peut disparaître à tout changement d'app.

## Fenêtre détachée (second écran)

- **`window.open()`** : partout, mais un geste de l'usager par appel [24] ; sur mobile, c'est un nouvel onglet, pas une fenêtre. La fenêtre ouverte est une page à part (nouveau contexte, nouveau `document`) : le worker v86 ne peut pas y être déplacé ; il faut soit garder v86 dans l'onglet d'origine et envoyer l'écran à la fenêtre (via `MessagePort`/`SharedArrayBuffer`, même origine, isolation croisée conservée si les en-têtes sont servis à la popup aussi), soit transférer l'`OffscreenCanvas` par `postMessage` (transfert possible entre fenêtres de même origine). Dans Chrome, les fenêtres ouvertes par `window.open()` partagent le groupe de contextes : le gel d'Energy Saver s'applique au groupe entier [27] — un onglet caché n'est pas gelé tant que la fenêtre détachée est visible, et réciproquement.
- **Document Picture-in-Picture** (Chrome/Edge 116, Firefox 151 bureau, jamais Safari ni mobile [23]) : fenêtre toujours au-dessus, une par onglet, ne survit pas à l'onglet, pas navigable, position non choisie par le site ; les éléments DOM y sont déplacés (le `<canvas>` d'affichage peut l'être). Bon candidat pour « la fenêtre invité en flottant », pas pour « sur le second écran » (position imposée par le navigateur).
- **Window Management** (`getScreenDetails`, permission `window-management`, `requestFullscreen({screen})`) : Chromium seulement [24] ; permet d'ouvrir la popup aux coordonnées d'un écran précis ou de mettre le canvas en plein écran sur un écran choisi. Ailleurs, l'usager déplace la fenêtre à la main.
- Sans ces API (Safari, Firefox pour le multi-écran), la fenêtre détachée de Kazo reste un `window.open()` placé par l'usager ; c'est déjà suffisant pour « déplacer la VM sur le second écran » à la main.

## Déchargement d'onglet et économiseurs de mémoire

Ce qui arrive à un worker v86 qui tourne dans un onglet non visible :

| Navigateur | Mécanisme | Effet sur la VM | Détection / reprise |
|---|---|---|---|
| Chrome (bureau) | **Memory Saver** (108) : décharge les onglets inactifs « depuis un certain temps » ; modèle d'apprentissage et délais modifiés en 2025-2026 (non vérifié) [26] | la page est **détruite** (comme fermée) : worker, mémoire wasm, état de la VM perdus ; disque OPFS intact jusqu'au dernier `flush()` | aucun événement avant ; au retour, rechargement automatique et `document.wasDiscarded === true` → restaurer depuis le dernier point de restauration. L'usager peut exclure un site (réglage, pas d'API) |
| Chrome (bureau) | **Energy Saver** (133) : gèle après > 5 min caché et silencieux si le groupe est « gourmand en CPU » (seuil calibré pour ~10 % des onglets) [27][43] | files de tâches suspendues ; le sort des dedicated workers n'est pas documenté (non vérifié) ; le temps de l'invité s'arrête | événements `freeze`/`resume` (Page Lifecycle). **Exemptions documentées** : audio/visio, périphériques (USB/HID/Serial/Bluetooth), **tenir un Web Lock ou une connexion IndexedDB qui bloque hors du groupe** [27] |
| Chrome | limitation des minuteries en arrière-plan (1/min après 5 min, « intensive throttling », 88) | ne touche que les `setTimeout` de la page ; un worker n'est pas limité (non vérifié pour 2026) | — |
| Chrome Android | gel des files de tâches après 5 min en arrière-plan (depuis ~69) [28] ; onglets tués sous pression mémoire [42] | gel : comme Energy Saver ; mort : comme Memory Saver | `freeze`/`resume` ; `wasDiscarded` |
| Edge | **Sleeping Tabs** : endort après 2 h par défaut (réglable) ; peut geler puis décharger sous pression modérée ; exemptions : audio, capture d'écran, DevTools, notifications [29][45] | endormi = page gardée en mémoire mais suspendue ; déchargé = détruit | `freeze`/`resume` (Chromium) ; `wasDiscarded` ; Memory Saver de Chromium aussi présent (non vérifié) |
| Firefox | **Tab unloading** (93 Windows, puis tous bureaux ; Android aussi) : décharge par LRU quand la mémoire système est critique ; exclut média en lecture, PiP, WebRTC ; épinglé = moins probable ; `about:unloads` ; pref `browser.tabs.unloadOnLowMemory` [30] | page détruite, rechargée au retour | pas de `freeze`, pas de `wasDiscarded` (non vérifié) : l'onglet revient sur `pageshow` avec une page neuve ; à détecter par l'absence d'état en mémoire |
| Safari macOS | limitation CPU/minuteries en arrière-plan ; proposition ancienne de tuer un WebContent sans page visible qui dépasse un budget CPU sur 15 min, sauf audio (non vérifié qu'elle ait été livrée) | ralentissement ; mort possible, non documentée | rechargement au retour |
| Safari iOS/iPadOS | **jetsam** du processus WebContent (pression mémoire ou changement d'app) ; boucle « tué → rechargé → tué » jusqu'à « A problem repeatedly occurred » [32][33] | page détruite, sans aucun signal JS avant ; la VM de E1 (1,4 Gio) serait tuée dès le boot | rechargement ; pas de `wasDiscarded` (non vérifié) ; seul `pagehide`/`visibilitychange` permet d'écrire un point de restauration **avant** de passer en arrière-plan |

Conséquences communes : (a) tout ce qui n'est pas sur disque OPFS au moment du déchargement est perdu, d'où l'intérêt du `flush()` périodique de E2 et d'un point de restauration à `visibilitychange: hidden` (E5 : 88 ms pour 256 Mio, 0,4 s pour 1 Gio en E1) ; (b) le gel arrête l'horloge de l'invité (Linux verra un saut de temps au `resume` ; les sons en cours produiront des xruns, E5) ; (c) tenir un Web Lock par disque (E11) a un effet de bord utile dans Chrome : il exempte du gel d'Energy Saver, mais pas de Memory Saver.

## Limites de l'étude

- Lecture seule : aucune mesure sur Safari, iOS, Android ni Samsung Internet ; E2 et E5 n'ont tourné que sur Chrome/Edge/Firefox de bureau.
- Les versions Samsung Internet sont déduites de la base Chromium (publiée jusqu'à 29 ; inconnue pour 30.x) : toutes marquées « ≈ ».
- Les règles de déchargement de Chrome ont changé en 2025-2026 (modèle ML, délais) sans page officielle à jour trouvée ; celles de Safari macOS ne sont documentées que par des bugs WebKit anciens.
- Les limites mémoire mobiles viennent de rapports de bug (iOS 17, Chrome 121) ; rien d'officiel, rien pour iOS 26/27 ni Android 2026.
- Pointer Lock sur Android (Chrome 144) : intention de livraison, pas de confirmation qu'elle a été livrée.
- Quota Chrome : MDN dit « 60 % du disque total » ; E2 a vu 10 Gio sur un disque presque plein : la règle réelle tient compte de l'espace libre (non vérifié).

## Ce que ça veut dire pour Os-x86

Chaque point est une proposition à valider, pas une décision.

1. **Socle minimal** (À valider) : Chrome/Edge ≥ 108, Firefox ≥ 111, Safari ≥ 16.4 (OPFS synchrone + OffscreenCanvas), Chrome Android ≥ 109. En dessous, Os-x86 refuse de démarrer avec un message clair plutôt que de dégrader.
2. **Hébergement Blazor et isolation croisée** (À valider) : SAB/`Atomics.wait` exigent COOP `same-origin` + COEP sur le document Kazo. En Blazor WASM hébergé, le serveur ASP.NET Core ajoute ces en-têtes quand le multithreading est activé [40] ; en autonome (hébergeur statique), c'est l'hébergeur qui doit les envoyer, et certains ne le permettent pas. COEP `require-corp` casse toute sous-ressource tierce sans CORP ; `credentialless` n'existe pas dans Safari. Proposition : Os-x86 fonctionne **sans** SAB (worker + `MessagePort`, comme E5) et n'utilise SAB qu'en option détectée par `crossOriginIsolated`, pour ne pas imposer d'en-têtes à tout Kazo.
3. **Mémoire** (À valider) : 512 Mio au plus par VM sur bureau (E1), 256 Mio sur mobile, et pas de VM du tout sur iOS tant qu'une mesure n'a pas montré qu'un WebContent survit avec v86 à 256 Mio. Memory64 : hors périmètre (Safari).
4. **Mobile = vue plein écran d'une VM de secours** (À valider) : une seule VM, 256 Mio, clavier et pavé tactile virtuels fournis par Kazo, Wake Lock demandé au lancement, point de restauration à chaque `visibilitychange: hidden`, reprise depuis le disque au retour. Pas de fenêtre par fenêtre (E4) en mobile.
5. **Survivre au déchargement** (À valider) : `flush()` OPFS périodique + journal d'écriture (E11), point de restauration à `hidden`, détection au retour (`wasDiscarded`, ou absence d'état en mémoire), et un Web Lock tenu par disque (exemption du gel dans Chrome). Afficher à l'usager que la VM a été arrêtée par le navigateur, pas par Os-x86.
6. **Fenêtre détachée** (À valider) : `window.open()` + écran envoyé par `MessagePort` (v86 reste dans l'onglet d'origine) comme chemin commun ; Document PiP comme option « flottante » sur Chrome/Edge/Firefox ; Window Management (Chromium) pour viser un écran. Pas de promesse « second écran » sur Safari.
7. **Deux API de verrouillage clavier** à abstraire (À valider) : `navigator.keyboard.lock()` (Chromium) et `requestFullscreen({keyboardLock})` (Firefox 151, Safari 26.4) ; toujours en plein écran ; Pointer Lock en bureau seulement.
8. **Presse-papiers** (À valider, lien avec E9/ADR 0065) : écriture après geste partout ; lecture : permission (Chromium), invite « coller » (Firefox), geste strict (Safari). Prévoir le chemin « bouton coller » comme chemin commun.
9. **Persistance** (À valider) : demander `persist()` après un geste, afficher le résultat, et sur Safari avertir de l'éviction à 7 jours sans visite (une VM non ouverte pendant une semaine peut disparaître) ; le quota Firefox de 10 Gio par site borne « base + différences + états » pour tous les profils Kazo d'un même navigateur.

**Fonctions marquées « non prises en charge ici »** (proposition, À valider) :

- Chrome / Edge (bureau) : aucune ; Memory64 non utilisé par choix.
- Firefox (bureau) : Window Management (second écran ciblé), COEP `credentialless` sans objet ; Keyboard Lock seulement via plein écran.
- Safari macOS : Document Picture-in-Picture, Window Management, Memory64, COEP `credentialless` ; Keyboard Lock seulement ≥ 26.4 et en plein écran ; persistance soumise à l'éviction 7 jours.
- Safari iOS/iPadOS (et Chrome/Firefox/Edge iOS) : Pointer Lock, Keyboard Lock, Document PiP, fenêtre détachée (nouvel onglet seulement), Memory64, VM > 256 Mio (et toute VM tant que non mesuré), survie en arrière-plan.
- Chrome Android : Pointer Lock (jusqu'à 144, puis souris physique seulement), Keyboard Lock, Document PiP, fenêtre détachée, Memory64/4 Gio sur builds 32 bits, survie en arrière-plan ; VM > 256 Mio sur appareils < 8 Go.
- Samsung Internet : comme Chrome Android, avec un décalage de versions non publié ; tout « ≈ » à vérifier sur appareil.
- Disposition mobile de Kazo (tous navigateurs) : fenêtre par fenêtre, fenêtre détachée, Pointer Lock, Keyboard Lock, plusieurs VM.
