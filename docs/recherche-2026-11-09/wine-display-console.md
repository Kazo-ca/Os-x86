## Implications
- D13 console programs are feasible with stock Wine and need no Wine patch. A guest agent in the i686 VM, a static binary that also handles the D15 run/track/stop operations, launches each program as 'wine prog.exe' (or through a small in-prefix launcher .exe) in its own cgroup. It uses forkpty when Kazo stdin/stdout is the terminal, and pipes when the program is redirected inside a Kazo pipeline, which matches Windows semantics (C19). Before launch it sets the pty size from the Kazo viewport (C22) and LANG=C.UTF-8 so the Unix conhost emits UTF-8 VT. It forwards Ctrl+C by writing 0x03 to the pty master (C20) and returns the exit status. Full 32-bit Windows codes need the launcher helper, because Wine truncates to 8 bits (C21).
- D13 also needs Kazo SDK work (new ADR) on the terminal side. VT output already passes through to xterm.js (C23), but the terminal is canonical-only and treats Ctrl+C as cancellation with status 130. Os-x86 needs: (a) a raw-tty contract that hands raw key bytes or escape sequences to the command with no line discipline or echo; (b) an 'interrupt' event that does not cancel the command, because Windows programs can catch CTRL_C_EVENT and keep running; (c) the viewport at launch. Without these, only line-oriented programs work. TUI programs and 'press any key' prompts would break, and a stray double echo is possible.
- Channel recommendation. Use one multiplexed framed protocol for control, stdio, window and input messages over a dedicated virtio-console port (virtio-1). Bulk pixels go through a shared surface heap in VGA VRAM, which the host reads directly (C07). The protocol must carry credit-based flow control, or Os-x86 must ship a small v86 patch adding host-side buffering, because v86 drops host-to-guest data when no buffer is posted (C02). Fallbacks: a TCP listener reached through network_adapter.connect (C05), which gives real flow control but shares the NIC that the D14 network policy must police; serial only for boot logs. Guest file access to the Kazo VFS uses 9p with a custom handle9p server scoped per launch (C06).
- The 'Wine ready' instant start must be a v86 snapshot taken after boot, with 'wineserver -p', explorer/services and the agent idle (C18, C09). Ship it zstd-compressed, or build it on first run per user and subsystem (D11). Snapshots become invalid on every v86 STATE_VERSION change and must be rebuilt (C09). After a restore, the agent must resync the clock and re-seed RNG. It must also regenerate per-user identifiers (machine-id, the Wine prefix's MachineGuid) so users who restore the same image are not identical. The NIC needs mac_address_translation or preserve_mac (C10). A custom 9p server must persist its fid state across a snapshot, or the guest must remount. For cold boots, take Boxedwine's explorer-timeout patch (10 s -> 120 s), since an emulated cold start overruns Wine's default (C17).
- Realistic option set for D13 GUI windows, from cheapest to best integration. All effort figures are guesses (low confidence).
- (A) One VM window per subsystem: the guest display through a worker-side OffscreenCanvas screen adapter (C08), with Xorg on Bochs VBE, a minimal WM or Wine virtual desktop, and a VMware absolute mouse (C30). Low effort (about 1-2 weeks). It doubles as the D15 'VM console', and every .exe appears inside that one window.
- (B) Per-application window by framebuffer slicing, a VirtualBox-seamless-style approach without its overlap problem: each launch runs in its own named Wine virtual desktop ('explorer /desktop=<id>,WxH'). The guest agent tiles the desktops without overlap on the big guest screen (at most 2560x1600, C07) and reports their rectangles, and the host cuts each into its own Kazo window. Menus and popups stay clipped inside their app's window, so no Kazo position API is needed and stock winex11 works. Medium-low effort (about 3-6 weeks). Limits: total area of about 4 MP, X server overhead, re-tiling on resize.
- (C) Remote-desktop stacks (Xpra HTML5, RDP RAIL like WSLg, SPICE): ready-made, but too heavy for one emulated core, and RAIL/SPICE lack per-window web clients (C27). Not recommended except as a throwaway prototype.
- (D) A custom Wine display driver, 'winekazo.drv', modelled on wineandroid.drv (C13): per-window surfaces backed by the VRAM heap with zero-copy flush, a Qubes-like message set (C26), direct input injection, and no X server in the guest. Best fidelity and lowest guest overhead. High effort (about 2-4 person-months for an MVP). It is an LGPL fork that must track Wine's internal driver API (38 header changes since 2025, C14), so it needs a pinned Wine version per Os-x86 release.
- (E) Upstream winewayland.drv plus a small guest 'bridge compositor' (libwayland-server, xdg_shell, wl_shm, wl_seat with an xkb keymap, data-device) that forwards each xdg_toplevel and its owner-relative subsurfaces to Kazo. This shifts the driver churn to upstream and fits Kazo's no-absolute-position model (C15). Medium-high effort (about 2-3 person-months), with one extra guest copy from wl_shm into VRAM. Risks: the driver is still 'experimental' in 11.0 (C12), and Greenfield cannot be reused under MIT (C28).
- Recommended staging: ship A for v1 together with full console support. Make B the first 'one window per .exe' experience. Decide between D and E only after a spike that measures virtio-console throughput, Wine warm/cold start inside v86, and winewayland against a minimal compositor in v86.
- True seamless windows (D/E) also require Kazo platform work. Today a window request has no position (C24), so the platform needs a 'pixel surface window' that a Os-x86 feature/service can create at runtime and that the v86 worker paints through a transferred OffscreenCanvas, because Kazo renders windows on the main thread and the Mono interpreter is busy there. It also needs owner-relative popup or overlay placement, or an absolute position API; focus, activation and z-order events back to the guest; pointer capture and raw keyboard codes; per-window title, icon and taskbar entries. WindowStyle.None already gives frameless click-through surfaces.
- D9 risk: an i686-only guest can only create win32 prefixes, which Wine 11.0 deprecates (C12). Os-x86 should build and pin its own 32-bit Wine, as Boxedwine does with build_wine.py (C16), and treat the x64 tier as the long-term home for Wine. 16-bit apps may also hit v86's missing 16-bit protected-mode features (C11).
- D14: because all guest traffic is NATed through v86's JS stack (C33), the 'each executable is a separate application' network prompt needs the guest agent to attribute connections. Options: a cgroup per launch with an agent-side transparent proxy, or a network namespace per launch. The host then holds the connection (no SYN-ACK) while the Kazo/Os-x86 permission window is open. The agent's own control link must stay outside that policy, which is one reason to prefer virtio-console over TCP for the agent link.
- Licensing for the MIT Os-x86 host: Boxedwine (GPL-2), the Xpra server (GPL-2) and Greenfield (AGPL-3) code must not land in the host package. Guest-image components (Wine LGPL, a winekazo.drv fork, the agent, Xorg) can live in the separate guest/engine package, as already agreed for copyleft engines.

## Open questions
- GUI target for the first release: (A) one VM window per subsystem, (B) one Kazo window per launched .exe through per-app Wine virtual desktops with framebuffer slicing (menus clipped inside the window), or wait for true seamless windows (D/E)?
- If true seamless windows are pursued: a custom Wine display driver (D, best fidelity, fork with a pinned Wine version and ongoing rebases) or upstream winewayland.drv plus a guest bridge compositor (E, less Wine churn, driver still experimental)?
- Will Kazo accept the SDK/platform additions that D13 needs: a raw-tty terminal mode plus an interrupt signal that does not cancel the command, and, for seamless windows, runtime-created pixel-surface windows painted from a worker plus owner-relative or absolute window placement? Each needs its own ADR.
- Exit codes: is the 8-bit truncated code from Wine acceptable for v1, or must Os-x86 ship a launcher helper .exe in the prefix so Kazo gets full 32-bit Windows exit codes (e.g. 0xC0000005)?
- Snapshot policy for an instant 'Wine ready': ship a prebuilt compressed state image (hundreds of MB, rebuilt on every v86 upgrade), or build it on each user's first run and store it per user/subsystem (storage quota in OPFS)? Is a minutes-long first boot acceptable?
- Agent transport: patch v86's virtio-console (host-side buffering), or keep stock v86 and rely on in-protocol credit flow control? Is a TCP-over-fake-network fallback acceptable, given that it shares the NIC policed by the D14 network permissions?
- Wine version policy for the i686 guest: pin a stable release (e.g. 11.0) and self-build it the way Boxedwine does, given that win32-only prefixes are deprecated upstream? What is the trigger for dropping i686 Wine in favour of the x64 tier?
- D14 attribution mechanism inside the guest: a cgroup per launch with a transparent proxy run by the agent, or a network namespace per launch? While the permission window is open, should the connection be held (SYN not answered) or refused at once with a retry later?
