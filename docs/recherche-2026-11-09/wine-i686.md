## Implications
- D9 looks feasible on paper but has no prior art. Every piece exists in Nov 2026: v86 gives a Pentium-4-class CPU with SSE2/SSE3, PAE and (since 2026-10-04) NX, and Alpine 3.24 x86, Void i686 and Buildroot all ship or build Wine 11 for i686. No one has published Wine running inside v86, so D9 should get a timed spike before it is locked. The spike should measure boot, wineboot, notepad, winecfg and a console .exe.
- D9 guest choice. Alpine 3.24 x86 is the natural default: v86 already ships Alpine build tooling, the image is small (musl, ~3 MB minirootfs, 29 MiB virt kernel), Wine 11.0 is stable, and the kernel is maintained (6.18.62, 2026-11-07). Void i686 is the fallback if newer Wine is needed (11.21). Buildroot is the option for a fully reproducible minimal image, but it builds without mingw, so it ships stub DLLs and the -msse2 change does not apply. Debian is out: trixie has no i386 kernel and bookworm has Wine 8.0. Arch32, Slackware and Tiny Core are stale or source-only for Wine.
- D9 kernel. Os-x86 should own its guest kernel config: CONFIG_VMSPLIT_3G (32-bit Wine needs it), virtio, 9p and a single CPU. Upstream x86-32 is being trimmed (i486 removed in 7.1, TSC-less CPUs in 7.2, highmem deprecation with a proposed VMSPLIT_2G_OPT default), and distro defaults could break Wine.
- D9 user experience. Running wineboot in the browser would likely take minutes. Build the image with the prefix already created, and ship a saved v86 state with the guest booted and wineserver warm (v86 initial_state). Starting an .exe then becomes 'restore state, run'. Default guest RAM should be 512 MB (256 MB is enough for console only); the hard ceiling is about 2 GiB inside v86's wasm32 heap.
- D16 (32-bit first). The i686 guest runs Wine's deprecated pure 32-bit mode (WINEARCH=win32, deprecated in 11.0). It still works through 11.21 and in shipped i686 packages, but there is no guarantee it will stay. Pin the Wine version per guest image and treat prefixes as disposable. Keep user data out of the prefix, for example on a 9p-mapped drive letter, because win32 prefixes cannot be converted to WoW64 prefixes.
- D16 DOS. Wine has not run DOS programs since 2018. MZ-only (DOS) binaries should not go through Wine. Send them to a FreeDOS VM on v86, which runs DOS 'very well', or to DOSBox in the guest. The D13 binfmt dispatcher should tell PE (MZ with a PE header) apart from pure MZ.
- D16 CPU limit. Wine 11.11 and later builds its 32-bit PE code with -msse2. v86 covers that, but it advertises no SSSE3, SSE4.x or AVX, so newer 32-bit apps or games that require those will fail. Compatibility claims should say this.
- x64 tier. A Linux x86-64 guest with Wine new WoW64 is the right target. One 64-bit prefix runs 16-, 32- and 64-bit .exe with no i386 Unix libraries, which is how Alpine x86_64, Arch and SBo ship Wine. Over time it can replace the i686 guest, though existing win32 prefixes must be recreated and apps reinstalled. v86 cannot host it because CPUID has no long-mode bit. The engine chosen after the benchmark needs long mode with at least an x86-64-v1 baseline (SSE2), and an x86-64-v1 distro such as Alpine or Debian amd64 keeps SSE4.2 and AVX optional in the engine. Expect the image to be about twice the i686 size (Alpine wine x86_64: 418 MiB installed vs 221 MiB).
- Licensing (Os-x86 stays MIT, copyleft engines in separate packages). Ship each guest image as its own package (for example 'Os-x86 Guest: Alpine+Wine') with a licence manifest. Host the full corresponding source (aports/Buildroot recipes plus upstream tarballs for Wine, the kernel, BusyBox and others) next to the image download. That satisfies LGPL-2.1 §4/§6 and GPL-2.0 §3 through 'equivalent access from the same place'. Aggregation does not affect the MIT host code. Boxedwine is GPL-2.0, which is another reason it fits only as the UI-only package decided in D9.
- D11 storage. If each user owns a full 0.5–1 GB copy of the subsystem in IndexedDB, quotas run out fast. A shared read-only base image (v86 9p fs.json/baseurl or a chunked disk) plus a per-user copy-on-write overlay and per-user prefix keeps the per-user cost to the overlay. Kazo's existing StorageSpaceMonitor and BrowserStorageManager can gate subsystem creation.
- D14 per-.exe network prompt. v86 sends only frames or payloads to the host, so Kazo cannot see which .exe connects. The Os-x86 permission system needs a guest-side agent. One design: netfilter NFQUEUE (or a Wine ws2_32 hook) matches each socket to its PID and .exe path, then asks the host over virtio-serial and waits for the user's answer. This is beyond this track and needs its own design.
- D13 console and GUI. Console .exe can run as 'wine prog.exe' on a guest tty bridged to the Kazo terminal. GUI .exe needs a display server in the guest (X11, or Wine's Wayland driver), and mapping Wine windows to separate Kazo windows needs a display bridge. Neither part is solved by the distro choice.

## Open questions
- Which guest base do you want: Alpine 3.24 x86 (musl, Wine 11.0 stable, smallest, v86 tooling exists), Void i686 (glibc, follows Wine dev 11.21), or a custom Buildroot image (Wine 11.0, no mingw, minimal and reproducible)?
- Wine version policy for the i686 guest: pin a stable release (11.0) and accept that the pure 32-bit mode is deprecated upstream, or follow development releases until upstream drops i386 hosts?
- Should wine-mono (.NET) and wine-gecko (MSHTML) be in the default image, adding roughly 0.15–0.25 GB, or installed on demand?
- What are the default guest RAM (512 MB vs 1 GB) and the per-user disk budget? Is a shared read-only base plus per-user overlay acceptable for D11, instead of full per-user copies?
- Should D9 be confirmed only after a timed spike of Wine inside v86 (boot, wineboot, notepad, winecfg, a console .exe), since no prior art exists?
- DOS route for D16: a separate FreeDOS v86 VM, or DOSBox inside the Linux guest?
- GUI path for D13: one guest X11 desktop shown in a single Kazo window, or a per-window bridge from Wine (X11/Wayland) to separate Kazo windows?
- Where will the corresponding-source bundle for each guest image be hosted (same server or CDN as the image), and who maintains the licence manifest?
