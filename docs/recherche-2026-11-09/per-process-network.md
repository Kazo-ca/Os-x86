- C18 [medium LB] Alternative: give each launch its own network namespace and a distinct routed source IP. This is kernel-enforced and inherited by all descendants (fork, exec, double fork). ## Missed (verifier)
- The stock Wisp adapter cannot be used in Kazo anyway: the Kazo relay is one WebSocket per stream on /api/proxy/tcp, not Wisp. So Os-x86 needs its own v86 network adapter in any case, and the SYN hold and prompt belong in that adapter with no v86 fork. v86 has no option to inject a custom adapter object (starter.js L251-272), but the NIC is always created (L274-276). Adapters only talk to the emulator through bus events 'net0-send' and 'net0-receive' (wisp_network.js L42-47, L248-251). handle_fake_networking and TCPConnection are exported from fake_network.js (wisp_network.js L4-9).
- Retransmission pitfall (fake_network.js L257-266, L285): each retransmitted SYN replaces the registered conn with a NEW object and re-calls on_tcp_connection. A holding adapter that just ignores the duplicate leaves tcp_conn empty, and the guest gets a RST. The adapter must re-register the newest conn on every retransmission and accept() that one on 'allow'.
- DNS bypasses Kazo: the default DoH path is a direct browser fetch() to cloudflare-dns.com (fake_network.js L58, L355-384). That skips the Kazo relay, the network.real.access grant and the server audit, and it may be blocked by CSP or COEP. Os-x86 should answer DNS itself, through the Kazo UDP relay (port 53 is allowed) or the HTTP relay. Because the host answers DNS, it can keep a per-source-IP map from DNS answers to IPs, so a prompt can name the hostname and not just the IP (the guest's SYN carries only an IP, wisp_network.js L222).
- The relay identifies the caller only by appId (AppNetworkGateway.cs:347). Every guest executable reaches the relay as the single Os-x86 app, so per-exe enforcement (D14) must live entirely in the Os-x86 host adapter. The guest's own policy and identity cannot be enforced server-side. MaxStreamsPerDevice = 4 is per DEVICE across all apps (ProxyContracts.cs:314, ProxyOptions.cs:234), so a VM competes with every other app for 4 streams unless the admin raises it.

## Implications
- Policy enforcement point (D14): enforce in the HOST, inside Os-x86's own network adapter (a BSD-2 fork or wrapper of v86 fake_network/wisp, wired to KazoTcpClient instead of Wisp), at the guest TCP SYN. The host is the only component guest code cannot tamper with. The adapter keeps SYNs in a pending map keyed by tuple, ignores retransmitted SYNs, shows the prompt, then on allow opens the relay stream and calls accept() (SYN-ACK), and on deny sends an RST (fast failure, like OpenSnitch 'reject'). It never drops silently, because silent drops cause 21-127 s stalls (C1-C3, C12).
- Attribution for Linux guests: at launch, a small root agent in the guest puts each launched program into its own network namespace with a distinct routed source IP (no NAT). It tells the host the mapping sourceIP -> LaunchId over a virtio-console port. The host keeps LaunchId -> identity {subsystem, user, guest path, SHA-256, caller app}. No userspace code runs on the guest data path, it works for static and Go binaries, and children inherit the identity automatically. This gives per-launch granularity (the exe plus everything it starts), kernel-enforced as long as launched programs run as an unprivileged guest user (C4, C5, C18).
- OpenSnitch: do not use it as the enforcement mechanism. Its attribution on i686 falls back to the slow /proc method, it fails open by default, it attributes Wine TCP to wineserver, it is GPL-3, and a host-side UI would need an HTTP/2 gRPC server in the browser. At most it is an optional, informational 'which process inside the launch' detail. If ever used, it ships in the separate guest-image package, not the MIT Os-x86 package (C6-C10, C14).
- Wine programs: robust granularity is per wineserver, which means per WINEPREFIX, because sockets are created and connected in wineserver (C13-C15). To treat 'each executable as a separate application', Os-x86 must run each identity in its OWN prefix, for example an overlayfs copy-on-write layer over a shared base prefix, with its own netns and IP. Whatever that exe launches (CreateProcess children, installers' payloads) then shares the identity, which matches the D14 rule 'inherits at most the caller's rights'. Telling apart exes that share a prefix (a game installed by setup.exe, a launcher and its game) is possible only cooperatively, through cmdline heuristics or a Wine patch, and a hostile .exe can bypass it (C16, C17).
- Consequence for the identity model: for Wine the natural 'application' is a bottle (prefix) whose first launched exe defines it. Installed programs live inside the installer's bottle. The design must decide whether a later launch of an installed exe joins the existing bottle (same network identity as the installer) or gets a new bottle (and cannot see the installed files).
- Windows VMs (long-term tier): the realistic v1 granularity is per VM (one subsystem = one identity), because the host sees only one NIC (C23). Per-exe needs a guest agent, either user-mode WFP with deny-first-then-ask-then-allow-next-time, or a signed kernel callout for true hold-and-ask. It should be a later option, not a promise (C24).
- Identity record for remembered decisions: compute it on the host at launch time. Os-x86 already knows which file it is launching (D13 binfmt hand-off, D15 interface), so no guest introspection is needed for the launched exe. Recommended v1 key: (Kazo user, subsystem, SHA-256 of the image) with the guest path shown in the prompt. On a hash change at the same path, show a Little-Snitch-style 'this program changed' prompt instead of silently reusing the rule. Authenticode or signer identity is deferred: browser .NET has SHA-256 but no RSA/X509 (C25, C26).
- Os-x86's own permission store, separate from Kazo's capability grants as D14 requires: stored per user (D11) and per subsystem. Each connection is checked in this order: Kazo grant of Os-x86 (network.real.access, dangerous, admin-approved) ∩ caller's rights cap (D14) ∩ Os-x86 per-identity rule ∩ relay policy (ports 80/443 by default, declared RealNetworkPorts, UDP 53/123, quotas). If an outer layer already refuses, Os-x86 should not show a prompt the user cannot make effective (C28).
- Fail-closed is required, unlike OpenSnitch's defaults. If no prompt can be shown (no interactive session, launch by a background caller, prompt timeout), apply deny with RST and record a 'missed prompt' notification. The prompt timeout should be about 15-20 s so Windows guests (about 21 s connect timeout) still get a usable answer. Linux guests tolerate longer waits (C10, C12).
- Coalesce prompts: queue all pending SYNs of one identity behind a single prompt, and let the user minimize it (Little Snitch). Offer Allow / Deny × {once, until the program exits, until the subsystem restarts, always}. Scope 'any destination' is the v1 default, with optional 'this host:port' (C27).
- DNS: the host already answers guest DNS (fake_network DoH). Keep doing that, without prompting, and keep a per-source-IP IP->hostname cache so prompts can say 'game.exe wants api.example.com:443' and rules can be per destination host (C2).
- UDP: the stock v86 Wisp adapter forwards no UDP except DNS, and the Kazo relay allows only UDP 53/123 by default. Prompts in v1 can therefore cover TCP only, with UDP (games, VoIP) as a later extension of the same host-side hook (C2, C28).
- Traffic not tied to a launch (guest system daemons such as dhcp, ntp or package managers, and commands typed in the wsl-like subsystem terminal) needs explicit identities, for example 'Subsystem <name> (system)' and 'Subsystem terminal session'. Otherwise unknown source IPs must fall to a default rule (C18).
- Relay quota: the Kazo relay's MaxStreamsPerDevice = 4 means one relay stream per guest TCP connection will starve a VM. A follow-up ADR for Os-x86 networking must cover quotas or multiplexing, independently of the permission prompt (C28).
- D15 interface: the 'run/track processes' contract can expose a launch's network identity and the decision state (allowed, denied, pending), and the permission window belongs to Os-x86's feature service, not the calling app. That keeps a calling app from answering its own prompts.

## Open questions
- What counts as 'one application' for Wine programs: each launched .exe in its own prefix or bottle (isolated files and registry, heavier, robust), or one bottle per installed program, so setup.exe and the game it installs share an identity? (Recommendation: one bottle per launched identity, created by overlayfs copy-on-write; programs installed by an installer stay in the installer's bottle.)
- Child processes: should an executable launched BY a launched program inherit the parent's network decision (kernel-enforced, recommended, matching D14's 'inherits at most'), or get its own prompt? Its own prompt is only cooperative inside one bottle or namespace and can be bypassed.
- Windows VMs: accept per-VM granularity for that tier (recommended), or commit now to a future Windows guest agent (user-mode WFP deny-then-ask, or a signed kernel driver)?
- Key for remembered decisions: SHA-256 of the image with the path displayed and a re-prompt when the hash changes (recommended), path only (survives updates but can be spoofed), or signer when available (needs a PKCS#7/X509 implementation that browser .NET lacks)?
- Prompt timeout and default: deny with RST after about 15-20 s (recommended, fits Windows' 21 s connect timeout), or wait as long as the guest keeps retrying?
- Scope offered in the prompt: per program for any destination only (simple, recommended for v1), or also per destination host:port?
- Should DNS queries ever prompt, or does the host always resolve them silently and prompt only at connect time with the hostname? (Recommendation: silent DNS.)
- How should traffic from the wsl-like subsystem terminal and from the guest's own system daemons be identified and governed: one 'subsystem' identity, or prompts per command?
- When the calling app lacks network.real.access, or the target port is outside the relay policy, should Os-x86 deny silently, or show an explanatory notification instead of a permission prompt?
- Who may answer: only the user owning the subsystem (D11), or can an admin pre-seed or lock Os-x86 network rules machine-wide, like Windows Firewall policy merge?
- Do launched programs run as an unprivileged guest user in the Linux guest (needed for per-launch isolation to mean anything), and is the guest agent allowed to run as root?
