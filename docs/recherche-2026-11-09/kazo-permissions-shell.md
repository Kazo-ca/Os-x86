## Implications
- D13 binfmt: today './setup.exe' returns 126 'cannot execute binary file' (ShellInterpreter.Scripts.cs:78-83) after the whole file is read as text. The generic binfmt ADR needs a Kazo OS change. Place a magic-number registry in RunPathAsync between the x-bit check and the text read, reading only the header bytes, and dispatch through the existing shebang route (LaunchCommandAsync with [path, ..args]). Streams, PPID, Ctrl+C token, elevation and exit code then come for free. Registration fits naturally on TerminalCommandManifest (for example a `binaryFormats` magic/offset list); this is an additive SDK change (ADR 0132). Keep 126 for unregistered binaries.
- D13 handler shape: the binfmt handler must be a Terminal-kind app, because Resolver.Resolve only returns Terminal commands. One manifest has one Kind, so Os-x86 ships at least three app ids: the feature service, the 'Subsystems' window app, and a terminal command such as `x86run` or the wsl-like command. The desktop/explorer double-click on .exe is a separate route through FileHandlers on an Os-x86 Window app.
- D13 console vs GUI: the handler can read the PE Optional Header Subsystem field (2 = GUI, 3 = console). For a console program, guest stdio is piped through TerminalExecutionContext. For a GUI program, the command asks Os-x86's display window app to open a window, then waits for the guest process and returns its exit code. If the GUI program were launched as a Window app instead, the shell would get 0, because no window exit-code API exists.
- D13 Ctrl+C: in canonical mode Ctrl+C is a one-shot cancellation of the whole line (TerminalPanel.razor:1132-1139). Os-x86 can map the first cancellation to guest SIGINT and escalate to SIGTERM/SIGKILL after a grace period, but a guest program that survives SIGINT cannot receive another Ctrl+C or keep reading stdin. Repeated Ctrl+C and raw keystrokes (vim, curses, wineconsole TUIs) would need either the undocumented trick of entering the full-screen session for keys while writing raw VT bytes to stdout, which TerminalPanel still forwards to xterm.js, or a new raw-tty mode in Kazo. Exit codes: return the guest code and follow 130/137/141.
- D13 x-bit: Linux semantics require +x before any binfmt runs (Scripts.cs:57-66). Downloaded .exe files probably lack it, so a decision is needed: keep execve semantics with the chmod hint, or exempt registered binary formats (WSL-like).
- D13 signals and ps: `kill <pid>` only distinguishes SIGKILL from a polite stop with 5 s grace (KillCommand.cs:10-21). Guest processes will not appear in Kazo ps or the Task Manager unless the OS adds a 'foreign process' API (argv, kill callback, accounting). StartChild is too bare (no argv, no kill notification, unsupported in workers), and KazoBackground jobs are capped per app.
- D14 declared permission for callers: the OS catalog is closed, so 'an app that launches through the interface needs a new declared permission' requires either (a) a Kazo OS catalog addition such as `x86.execute` with a classification and risk sentence, or (b) a provider-declared permission mechanism tied to the D10 resolver. Topic permissions only gate the topic bus, and in code they are auto-granted at login despite ADR 0040.
- D14 'at most the caller's rights': Kazo never intersects rights; a child runs with its own manifest grants (AppLifecycleOrchestrator.cs:1049-1062). Os-x86 must compute effective rights itself: Os-x86's own grants ∩ the caller's grants ∩ per-executable decisions. Caller identity and grants read from the ambient KazoExecutionContext can be forged (Enter is public, and the docs say Kazo is not a sandbox), so D10 resolution should have the OS hand the provider a trusted caller identity and capability snapshot (an OS change). Otherwise Os-x86 can only rely on OS-stamped channels (topic PublisherAppId, intent SenderAppId).
- D14 own permission system: Kazo's grants are keyed by (appId, userId, capability) from manifests, and Os-x86 cannot write grants or reuse the approval overlays, which are Platform.Core and not SDK. A separate Os-x86 permission store is therefore required, as the user decided. A natural layout mirrors app-permissions.config: user decisions in ~/.config/<osx86AppId>/exec-permissions.config (filesystem.private.*), admin pre-decisions in /etc/<osx86AppId>/ (readable with private.read, written via sudo or admin), edited with the public ConfigDocumentEditor, plus an audit trail in Os-x86's own log because daemon logs are system-only.
- D14 runtime prompt UI: a Service cannot show UI, and notification actions do not call back. The Os-x86 service should launch or activate its own Window app (Intents.LaunchAsync, apps.launch is normal), passing the pending request in a custom intent, and get the answer back over an owner-only topic channel or a file. If the guest was started from a terminal, a text prompt is possible but competes with the guest's own stdin. While the prompt is pending, the network bridge holds the guest connection; a deny returns a reset or unreachable to the guest.
- D14 enforcement point: per-executable network decisions are only enforceable if all guest traffic goes through Os-x86's main-thread .NET bridge to AppNetworkGateway (KazoTcpClient, KazoUdpClient, KazoClientWebSocket). Worker gateways cannot open sockets, and direct fetch/WebSocket from the v86 JS worker would bypass Kazo entirely. Attributing packets to a guest executable needs a guest-side agent or shim (cooperative Linux guest, or Wine socket hooks).
- D14 two-layer consent: at the Kazo level, Os-x86 itself needs network.real.access (dangerous, admin password, approved once). If the network bridge lives in an auto-started session service (Interactive:false), the approval is deferred until Settings ▸ Permissions or an interactive launch, so Os-x86's first-run flow must handle 'not yet approved'. Relay limits also apply to all guests at once: TCP 80/443 by default, static RealNetworkPorts, BlockedPorts, 4 streams per device. Os-x86's per-executable prompt is a second, user-level layer under that grant and must respect Kazo's `block` policy and denials.
- D11 storage tie-in: per-user subsystems and disk images can only use the app-private area ~/.config/<appId>/ (filesystem.private.*). Placing them elsewhere in the home folder requires the broad filesystem.user-home.* capability.

## Open questions
- What identifies an executable for Os-x86 permissions: content hash (SHA-256), guest/Kazo path, path+hash, or a publisher signature? And does an updated binary keep its decisions or get prompted again?
- Who may answer the per-executable network prompt: any session user (user-level, under the admin's one-time approval of Os-x86's network.real.access), or does it need an administrator like Kazo's dangerous capabilities? Can an admin pre-allow or deny executables machine-wide in /etc/<appId>/?
- Which prompt choices and default: Allow once / Always allow / Deny / Always deny? Deny-by-default for unattended guests (no session UI) or hold the connection? What timeout before treating 'no answer' as deny?
- Beyond network, which actions of a guest executable get per-executable runtime prompts (access to Kazo files outside the VM sandbox, clipboard, devices, launching Kazo apps)?
- Is Os-x86 allowed to require Kazo OS changes, and which ones: (a) binfmt registry in hsh, (b) a new OS capability or a provider-declared permission for callers of the D10 interface, (c) trusted caller identity and grants handed to D10 providers, (d) foreign guest processes visible in ps/kill/Task Manager, (e) raw-tty terminal mode? Or must v1 live entirely within the current SDK?
- Should `./setup.exe` require `chmod +x` (Linux execve semantics) or be exempt when its magic matches a registered format (WSL-like)?
- For a console guest started from the terminal, when a permission prompt is needed: ask inline in the terminal (conflicts with guest stdin) or always open the Os-x86 consent window on the desktop?
- Ctrl+C semantics for console guests: accept one-shot cancellation (SIGINT then escalate to SIGKILL after grace), or require repeated Ctrl+C and raw keys (needs full-screen key mode or an OS change)?
- Should guest processes appear in Kazo's ps and Task Manager (needs an OS change), or only inside the Subsystems app and the wsl-like command?
- How should the D10 interface carry the 'new declared permission': a Kazo catalog capability classified normal (granted silently at install) or dangerous (admin approval at the caller's first launch)?
