## Implications
- D10 cannot be built on today's kernel. Five things block it: (1) a caller's .kazoapp cannot carry the contracts DLL (only declared assemblies are packed, #419); (2) the install-time API check refuses any reference to an assembly the caller does not ship and the runtime cannot load; (3) the loader loads only declared entry and component assemblies; (4) no cross-app service registry exists; (5) the build boundary forbids [Inject] of non-SDK types and of IServiceProvider. 'GetService<T>' must therefore be a new SDK gateway plus facade (ADR 0055 §4), not ASP.NET's IServiceProvider.
- Returning null requires the contracts assembly to be loadable even when Os-x86 is NOT installed. The caller's own code references the interface types, so the runtime resolves that assembly when the method runs; if it cannot, the caller gets a FileNotFoundException instead of null. So either every caller ships the contracts DLL (needs #419 'libraries'), or the OS ships it (SDK-style, like IKazoTerminal and IKazoFileView in ADR 0148).
- Type identity: the caller and Os-x86 must bind to the SAME loaded contracts Assembly. Today 'first loaded with that simple name wins, version ignored' (InstalledAppsBoot.cs:300-306), so a v1 copy in a caller could shadow the v2 that Os-x86 was built against and cause MissingMethodException. An ADR needs a shared-library rule: one copy per simple name, the highest compatible version chosen and loaded before any consumer (an ALC.Resolving handler like InstalledAppSatellites can serve it), installs refused across incompatible majors, and contracts kept binary-additive within a major (mirror the SDK rules of ADR 0019/0114; versioned contract ids like '.v1', as intents use).
- Resolution must be lazy and keyed by a contract name declared in the provider's manifest, so the catalog knows providers at boot without loading Os-x86 code. ADR 0148 rejected a global DI service for exactly this reason. KazoComponentHost.ResolveAsync is the template (platform, then admin-selected, then providers in order, skipping disabled or invisible apps, with load failure falling through), but it must return null instead of Unavailable, and it must accept a Service app, which today's component rules forbid.
- Because providers load from the VFS, resolution is naturally ASYNC (e.g. GetAsync<T>). That differs from the synchronous ASP.NET GetService<T>(); a synchronous form could only answer for providers whose assembly is already loaded.
- Naming: the contracts NuGet must not use a 'Kazo.Os.*' id outside the allowed pattern, or every caller's build fails with KOSAPP0030. Use 'Kazo.Os.Apps.X86.Contracts', 'Kazo.Os.AppSdk.X86' (only if it is a real Kazo SDK library) or an id without the Kazo.Os. prefix.
- Optional dependency semantics: if a caller declares Os-x86 as an Optional dependency WITH a MaximumVersion and an out-of-range Os-x86 is installed, the CALLER is dropped from the catalog. Callers should declare Optional with no MaximumVersion and express compatibility by contract version, or the ADR should change optional-dependency semantics to 'treated as absent'.
- D12: kazopkg and the Store do not resolve or check dependencies today; an app with a missing required dependency installs, then silently drops out of the catalog at boot. The SDK install API needs apps.manage and admin approval, so a 'request install of an optional dependency' call needs a new, lower-privilege, user-approved API.
- D14 rights: the component precedent (ADR 0148 §4) runs provider code with the CALLER's gateways and capabilities, which matches 'at most the caller's rights'. But Os-x86 also keeps per-user subsystem state and a long-lived VM service (D11). The most consistent shape: Os-x86 runs as a Service app with its own context, and the OS hands each caller a facade bound to an OS-verified caller identity (appId, userId, pid, capabilities). The provider must never trust the ambient KazoExecutionContext, which an app can fabricate.
- D14 declared permission: today it cannot be declared (validator allows only AppCapabilities or topic permissions). Choose either a curated OS capability (ADR 0049 classification and risk sentence) or a generalisation of ADR 0040's app-declared permissions with ICapabilityGrantRepository and mandatory approval.
- D14 per-executable network prompt: Os-x86's own permission system can be truly enforced against guest programs, because they are sandboxed inside v86 and every packet passes through Os-x86's emulated NIC. Against other .NET apps it is only cooperative: all apps share one ALC and 'run with the same rights as the OS'. Kazo has no generic SDK prompt API, so Os-x86 shows its own window.
- Updates: Os-x86 assemblies (contracts included) cannot be unloaded. An Os-x86 update while it is loaded applies only at the next OS start, and callers keep the old contract version until then. Removing Os-x86 at run time must make live facades fail gracefully, since the code stays in the page.
- Os-x86's .NET side must declare Execution = MainThread (an installed-app rule). The v86 engine and Wine guest run in JS/wasm Web Workers loaded from Os-x86's wwwroot (served at _content/<assembly>/ by ADR 0206/0225).
- A feature-resolution gateway is a public SDK addition, so a new SDK minor version. Callers must raise their SdkCompatibility minimum, and older Kazo OS versions will refuse them at install.
- Kernel gaps an ADR series must fill (next free ADR 0241). (G1) Finish #419: pack, hash, API-check and load an app's own libraries (ProjectReference and non-OS NuGet), refusing OS assembly names. (G2) Shared contract libraries: one copy per simple name, highest compatible version, loaded before consumers, install refused when majors conflict, built-in shadowing forbidden. (G3) A manifest field for providing a service contract (contract id 'vendor.feature.vN' plus a type in the entry assembly), allowed for Service apps, indexed by the catalog without loading code, honouring per-user visibility, with optional admin choice when several providers exist (ADR 0156 model). (G4) An SDK gateway on IAppExecutionContext plus a static facade (e.g. KazoFeatures.GetAsync<T>(contract)) whose default implementation returns null and which lazy-loads the provider; decide whether using it needs a capability. (G5) The OS passes a verified caller identity to the provider, so the provider can make per-caller facades, attribute child processes to the caller's process tree, and cap rights. (G6) Generalised app-declared permissions with an approval UI that shows the provider's own description and risk sentence. (G7) Dependency resolution in kazopkg and the Store, plus a user-approved 'request install' SDK API, and an optional dependency outside its version range treated as absent rather than fatal. (G8) Install-time API check made deterministic: judge against what the OS ships and the declared shared libraries, not against whatever the page happens to have loaded.

## Open questions
- Where do the Os-x86 contracts physically live? (a) In a Kazo SDK library (e.g. Kazo.Os.AppSdk.Subsystems) in the OS boot bundle: simplest, matches ADR 0148, always loadable so null works, but ties contract changes to Kazo SDK releases and its freeze rules. (b) Os-x86's own contracts NuGet, carried by every caller (needs #419 plus a shared-library version rule). (c) A separate 'shared library' kazopkg package that callers and Os-x86 both depend on, installed with the OS dependency resolver from D12.
- What NuGet id should the contracts package use? It cannot be 'Kazo.Os.X86.Contracts' (KOSAPP0030). Pick 'Kazo.Os.Apps.X86.Contracts', a Kazo SDK id, or an id outside the Kazo.Os. prefix.
- Should resolution be async (GetAsync<T>, because the provider may have to load from the VFS) or sync (GetService<T>, which returns null whenever Os-x86's assembly is not loaded yet)?
- Should the resolved object be an in-process typed facade (fast, same ALC, identity enforced only cooperatively) or a broker proxy over an OS message channel (works from Web Workers later, identity stamped by the OS)?
- Should every caller get its own facade, bound to its OS-verified identity (needed for D14 rights capping and per-executable permissions), or one shared singleton?
- May several apps provide the same contract (an alternative x86 engine later), with the administrator choosing as in ADR 0156, or is there exactly one provider per contract?
- Is the new D14 permission a curated OS capability in AppCapabilities, or an Os-x86-declared permission (extending ADR 0040 beyond topics)? Does using the feature-resolution API itself need a capability?
- Should a personal (per-user) install of Os-x86 be refused, since D11 says the admin installs it system-wide, or simply ignored by the resolver?
- Should an Optional dependency installed outside its version range be treated as absent (resolver returns null) instead of dropping the caller from the catalog? That changes existing catalog semantics and needs an ADR that supersedes the current behaviour.
- When Os-x86 is removed or updated while callers hold facades (its code cannot be unloaded), what should callers see: exceptions, a 'feature gone' event, or nothing until the next start?
