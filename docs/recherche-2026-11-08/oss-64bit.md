# oss-64bit

## Summary
This is a survey of x86-64 emulation in the browser as of November 2026 and whether x64 Windows can run inside a browser-hosted OS. It was read-only, with one exception: I saved one temporary file, features.json, in the session scratchpad. WebFetch also saved three PDFs on its own under the .claude tool-results folder.

**QEMU, upstream vs. the ktock fork.**
- Upstream QEMU merged initial Emscripten host support on 2025-05-06 and shipped it in QEMU 10.1.0 (2025-08-26). That version only runs 32-bit guests, using TCI, QEMU's slow built-in interpreter.
- Building with --cpu=wasm64 (Memory64) for 64-bit guests on TCI was merged on 2026-01-16 and is in QEMU 11.0.0 (2026-04-21). wasm32 Emscripten builds were removed at the same time, so configure now stops with "wasm64 must be specified". A --wasm64-32bit-address-limit flag targets engines that only support wasm32, such as Safari, with a 4 GB cap.
- The JIT backend that translates guest code to Wasm (TCG) is not in mainline as of v11.1.x: there is no tcg/wasm* directory. Its v4 series (33 patches, January 2026) was still under review, and a maintainer rejected an earlier design in August 2025.
- JIT and multi-threaded TCG (MTTCG) exist only in the experimental ktock/qemu-wasm fork. It is GPL-licensed, its default branch was last pushed 2026-02, its demos boot x86_64 Alpine with 512 MB, and recent community issues include a wrong POPCNT result in the wasm backend.
- In the FOSDEM 2025 talk (auto-generated transcript), pigz on an x86_64 guest took about 40 s on Bochs, about 30 s on QEMU-Wasm, and about 7–8 s on QEMU-Wasm with 4 threads. The slides say the Wasm backend is "still slower than other backends".

**Other candidates.**
- **container2wasm** (Apache-2.0, v0.8.5, 2026-11-04): uses Bochs for x86_64, TinyEMU for riscv64, and qemu-wasm for browser builds. It provides networking (browser fetch or WebSocket) and 9p folder mapping, which are good patterns to reuse.
- **Blink** (ISC): x86-64 Linux user-space only, mostly not system-level. It builds with Emscripten, but its JIT writes native code, so in wasm it would most likely run as an interpreter.
- **JSLinux:** now offers a closed-source x86_64 Alpine guest (PAE/NX, SSE4.2, AVX2/AVX-512, APX).
- **Bochs 3.1** (2026-08-23, LGPL): adds UEFI/OVMF (boots Windows Server 2025) and raises the host memory limit to 8 GB. It is an interpreter.
- **CheerpX 1.4.0** (2026-10): still 32-bit only and proprietary. The free licence covers use only from Leaning Tech's CDN; self-hosting needs a paid licence.
- **v86** (BSD-2, very active): 32-bit only. The 64-bit issue #133 has been open since 2017, and the author estimates 3–6 months of full-time work with nobody on it. NX-bit support was merged on 2026-10-04; missing NX had blocked 32-bit Windows 8/10. Its docs say each JIT module is costly, so only a few thousand can be generated.
- **Box64:** runs Linux x86_64 programs on ARM64, RISC-V and LoongArch hosts and has no wasm target, so it serves as a design reference only.
- **Running .exe files without Windows:** Boxedwine (GPL-2; 32-bit Wine, no JIT in its wasm build, "still slow") and ExeBrowser, which is built on it.
- **Nothing found boots real x64 Windows in a browser.** nanokrnl (July 2026) runs an NT-like Rust kernel on its own small x86-64 emulator, not real Windows.

**WebAssembly constraints.**
- A wasm32 memory is capped at 4 GiB. A 64-bit memory is capped at 16 GiB by the JS API.
- Memory64 shipped in Chrome/Edge 133 and Firefox 134 (early 2025) and Node 24. Safari has it only behind a flag in Technology Preview 251.
- Memory64 costs 10% to over 100% in speed because the engine must check bounds on every memory access (SpiderMonkey, January 2025).
- Threads need SharedArrayBuffer, which requires cross-origin isolation (COOP/COEP headers).
- SIMD and tail calls are supported everywhere. JSPI (calling async JS from wasm without Asyncify) is in Chrome 137, Firefox 153 and Safari 27. Stack switching is behind a flag only.

**What Windows needs.**
- **Windows 8.1/10 x64:** PAE, NX, SSE2, CMPXCHG16b, LAHF/SAHF and PrefetchW; 2 GB RAM.
- **Windows 11:** adds SSE4.1, plus SSE4.2/POPCNT from 24H2 on (press reports, cannot be bypassed). It also needs 4 GB RAM, 64 GB of disk, UEFI with Secure Boot and TPM 2.0. The TPM, Secure Boot and RAM checks can be skipped at clean install with the LabConfig registry keys.
- **Windows 7 x64:** 2 GB RAM, BIOS boot, no TPM. It is the easiest x64 Windows to target.
- QEMU's x86_64 CPU emulation provides the required instructions. In the browser, the TPM emulator swtpm and the OVMF UEFI firmware would still need porting or packaging.
- Licensing: Windows images cannot be redistributed, and each VM instance needs its own licence, so users must bring their own media and key.
- ReactOS 0.4.16 (2026-08) is released as i386 only; its x64 port is immature and has no WoW64.

**Verdict.** Native-hardware Windows 10/11 x64 in a browser tab is impractical today, though not strictly impossible. The emulated CPU features exist (QEMU x86_64 on wasm64, Bochs), but:
- the JIT is not upstream;
- performance is very low (my estimate, with no measurements: tens of minutes to hours to boot);
- Windows 10/11 RAM needs collide with the 4 GB wasm32 cap, and Memory64 is slower and missing on Safari;
- Windows 11 needs 64 GB disk images;
- no one has documented a successful boot.

A realistic tiered plan:
1. 32-bit system emulation with v86, covering DOS, Win9x/2000/XP, ReactOS and 32-bit Linux, plus possibly running Win32 .exe files through Boxedwine.
2. x86-64 Linux through qemu-wasm or container2wasm on wasm64, with 9p shared folders and networking.
3. Experimental x64 Windows 7, then 10, with 11 last, all with user-supplied media.

## Implications
- Do not plan to write a new x86-64 CPU from scratch for v1. Wrap an existing core behind a Kazo OS 'Hypervisor' abstraction: v86 (BSD-2, JIT, 32-bit) first, then QEMU-on-wasm64 (GPL-2) for x86-64. Keep the abstraction so the core can be swapped, since the upstream QEMU wasm JIT is still unmerged.
- x64 Windows guests effectively require wasm64 (Memory64) builds: Windows 10 x64 needs 2 GB and Windows 11 needs 4 GB of guest RAM, on top of the emulator's own heap, JIT cache and device buffers. wasm32's 4 GiB total cap makes Windows 11 unreachable and Windows 10 marginal, so plan x64 Windows only for Chromium and Firefox, which have Memory64.
- Safari/iOS will not run wasm64 builds in 2026 (Memory64 only behind a Technology Preview flag). Either accept no x64 support on Safari, or ship a second build using QEMU's --wasm64-32bit-address-limit (4 GB cap, so only 32-bit or Linux guests in practice).
- Multi-vCPU (MTTCG) and threaded emulators need SharedArrayBuffer, so Kazo OS (or at least the emulator's origin or iframe) must be served with COOP same-origin plus COEP require-corp or credentialless. This affects every third-party resource Kazo OS embeds, so decide it at the OS level, possibly by isolating the emulator in its own cross-origin-isolated worker or origin.
- Run the emulator core as a separate WebAssembly module in a dedicated Web Worker, not inside the Blazor/.NET runtime. A C# emulator such as MsDos.Clone would run inside .NET's WebAssembly runtime and could not cheaply JIT x86 into new wasm modules. The Kazo OS side (C#) should talk to the worker through a message bridge (postMessage or SharedArrayBuffer ring buffers).
- Shared folders with the OS map naturally to virtio-9p, which v86, QEMU and container2wasm all support, backed by a Kazo OS file system bridge (Emscripten FS, OPFS or IndexedDB). Networking maps to existing patterns: a Fetch-API network stack inside the browser (CORS-limited) or a WebSocket relay to a server-side network proxy (container2wasm c2w-net-proxy and c2w-net). These are the natural integration points for 'use OS resources'.
- Dynamic code generation requires the page's Content-Security-Policy to allow 'wasm-unsafe-eval'; Blazor WASM already requires it. JIT design must respect per-module cost and a practical limit of a few thousand modules: compile only hot code, page-granular, with eviction.
- The licence split argues for the Marketplace-module option. QEMU (GPL-2.0), Boxedwine (GPL-2.0) and Bochs (LGPL-2.1) cannot be merged into the CC BY-NC kernel as one combined work, so they should ship as a separately downloaded, separately licensed package. Os-x86 would have to be GPL-2.0 if it contains QEMU code. A permissive core (v86 BSD-2, Blink ISC, Box64 MIT) keeps the MIT licence possible.
- CheerpX is a poor fit for a downloadable or offline Marketplace package: it is 32-bit only, proprietary, and free use is limited to Leaning Tech's hosted CDN; self-hosting needs a commercial licence.
- A tiered roadmap is realistic. Tier 1: v86 32-bit (DOS, Win9x/2000/XP/Vista 32-bit, ReactOS, 32-bit Alpine/Debian); NX was merged in October 2026, so Windows 8/10 32-bit can be investigated. Tier 1b: run individual Win32 .exe files without a Windows install via Boxedwine-like Wine-in-wasm (slow, no JIT). Tier 2: x86-64 Linux 'subsystem' via qemu-wasm or container2wasm on wasm64, or Blink for user-space ELF only. Tier 3 (experimental): Windows 7 x64 (BIOS/SeaBIOS boot, no TPM/UEFI), then Windows 10 x64, then Windows 11 (needs OVMF, a TPM bypass or a wasm-ported swtpm, SSE4.2/POPCNT, 4 GB+ RAM, a 64 GB virtual disk).
- Windows media must be bring-your-own (user ISO and licence per instance). The subsystem installer should let users import their own media and never host Windows images; ReactOS (32-bit) is the only redistributable Windows-compatible guest.
- Storage needs a sparse, streaming disk design: Windows 10 x64 needs at least 32 GB and Windows 11 at least 64 GB of virtual disk. Use copy-on-write overlays in OPFS or IndexedDB and lazy HTTP range fetching, and watch browser storage quotas.
- Use snapshot/restore (v86 save/restore, QEMU migration, nanokrnl-style fast-boot snapshots) to hide long boot times; this matters most for heavy guests.

## Risks
- No public evidence that Windows 7, 10 or 11 x64 has ever booted to a usable desktop in a browser tab; committing to it as a deliverable is high-risk and may never reach usable speed.
- Performance: upstream QEMU on wasm is interpreter-only (TCI); the JIT exists only in an experimental fork, its upstreaming had stalled as of January 2026, and it is still slower than QEMU's native JIT backends. Combined with the 10% to over 100% Memory64 slowdown, Windows 10/11 boots could take tens of minutes to hours (estimate, not measured).
- qemu-wasm's default branch is dormant since 2026-02 and has open correctness bugs (wrong POPCNT, Asyncify crashes, idle 100% CPU); depending on it means maintaining a fork.
- Memory pressure: browser tabs commonly fail to allocate multi-GB memories well below the 4/16 GiB theoretical caps (commit limits, fragmentation), especially on 8 GB machines and mobile.
- Cross-origin isolation (COOP/COEP) may break existing Kazo OS features that embed third-party iframes, images or scripts without CORP/CORS headers.
- Licence contamination: copying QEMU or Boxedwine code into the MIT Os-x86 repo or the CC BY-NC kernel would violate the GPL; the CC BY-NC 'NonCommercial' clause is also not an OSI open-source licence, which may disqualify Kazo OS from CheerpX's free FOSS tier.
- Windows licensing: Microsoft licences cover one physical or virtual instance; distributing preinstalled images or helping bypass activation would be infringing; bypassing the Windows 11 TPM/Secure Boot checks puts installs in an unsupported state.
- Windows 11 24H2/25H2 hard-require SSE4.2/POPCNT and future releases may raise CPU baselines further (for example AVX2 or newer), increasing emulation burden and cost.
- Safari/iOS users would get no x64 support until WebKit ships Memory64.
- Process note: this research saved one scratch file (features.json) in the session scratchpad, and WebFetch auto-saved PDFs under the .claude tool-results folder; no project files were touched.

## Open questions
- Is booting full x64 Windows (7/10/11) a firm requirement for the first version, or an aspirational later tier? Are boot times of many minutes and slow interactive use acceptable for it?
- Is the main goal to run individual .exe programs (a Wine-like compatibility layer, no Windows install), or to install a complete Windows OS as a subsystem, or both?
- Which browsers must be supported? Is Safari/iOS required (it rules out wasm64/Memory64, which caps memory at 4 GB)?
- Can Kazo OS be served cross-origin isolated (COOP/COEP headers) globally, or must the emulator run in its own isolated origin or iframe?
- Licensing policy: may the Marketplace module be GPL-2.0 (needed for QEMU or Boxedwine), and may the Os-x86 repo be relicensed from MIT to GPL-2.0 if QEMU code is used? Is a proprietary dependency like CheerpX acceptable at all?
- Build vs. adopt: reuse an existing emulator core (v86/QEMU/Bochs) compiled to wasm, or write a new C# emulator in the style of MsDos.Clone that runs inside the Blazor runtime (much slower)?
- Is a server-side component acceptable (WebSocket network relay, disk-image streaming), or must everything run purely client-side and offline?
- Where should guest disk images live (OPFS/IndexedDB inside the browser vs. Kazo OS shared storage or a server)? What storage quota is acceptable, given Windows 10 x64 needs 32 GB or more and Windows 11 64 GB or more?
- What minimum user hardware do you target (e.g. 8 GB vs 16 GB RAM laptops)? This decides whether 2–4 GB Windows guests are even viable.
- For the Linux subsystem: full-system emulation (a kernel plus a distribution), or user-space x86-64 ELF only (Blink-style), mapped onto Kazo OS processes?
