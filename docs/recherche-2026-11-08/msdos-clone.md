# msdos-clone

## Summary
Analysis of werddomain/MS-DOS, branch copilot/create-webassembly-winform-clone. Local clone root: <scratchpad>/repos/msdos/MsDos.Clone. All paths below are relative to that root. Only source code and markdown were read.

WHAT IT IS. "winform clone" means an MS-DOS 4.0 clone with two front ends, a WinForms desktop app and a Blazor WebAssembly app, sharing one platform-neutral core library (MsDos.Core, net8.0). The core reaches the outside world through three interfaces: IGraphicsRenderer, IEventRegistry and IStreamProvider. It is not a WinForms-style UI toolkit for Blazor. The solution has 4 projects (Core, Blazor, WinForms, Tests/xUnit), about 29k lines of code, all on .NET 8 (Kazo OS is on .NET 10). Nothing enables AOT or threads, so in the browser it runs on the Mono IL interpreter plus the Jiterpreter.

EMULATOR ARCHITECTURE. The CPU is a single class, Cpu8086 (2,353 lines). It decodes with one giant switch. Prefixes are handled by calling DecodeAndExecute recursively. Flags are computed right after every operation, and parity uses an 8-step loop. A CpuModel enum (8088/80186/80386) selects how ambiguous opcodes behave.
- 32-bit coverage is partial. The 0x66 operand-size prefix works on many instructions (EAX…). The 0x67 address-size flag is toggled but never used, so there is no SIB byte and no 32-bit ModR/M addressing.
- LGDT/LIDT/LMSW and MOV CRn only store values. There are no descriptor caches, no privilege levels, no paging and no CPU exceptions (#GP/#PF/#UD). Unknown opcodes run as a NOP and log a warning.
- Memory is a flat 1 MB byte[] (no A20, no memory-mapped I/O routing). I/O ports use a per-port delegate table (IOPortBus).
- The BIOS is emulated in C# (HLE): an INT instruction raises an event, and the C# handler runs and then pops the stack frame. The IVT points to IRET stubs at E000:0000. A real BIOS ROM can optionally be loaded.
- DOS works both ways: an emulated DosKernel (INT 21h, memory blocks, EXEC) with a C# COMMAND.COM, and native boot of real MS-DOS from a floppy or hard-disk image. In native mode, vectors 20h–28h go through the IVT to the real DOS.
- Emulated devices: PIC master/slave, PIT, DMA 8237, floppy controller µPD765, CMOS/RTC, a PC speaker (raises an event only), CGA register tracking, INT 13h in CHS mode only, an INT 33h mouse, a stubbed 8042 keyboard controller, a FAT12/16 reader with MBR detection, and a blank 32 MB hard disk.
- Timing counts instructions, not real time: one PIT tick per instruction.

BROWSER INTEGRATION. Everything runs on Blazor's single thread. The loop runs 50,000 instructions, then waits (Task.Delay(16) in managed mode, Task.Delay(1) in native mode). A blocking wait from the guest rewinds IP and yields until input arrives. Rendering is text mode only: each frame the cell grid is sent to JS, which draws every cell with fillRect + fillText. DrawPixel does nothing in Blazor, and VideoMemoryMapper is never called, so graphics modes and direct video-RAM writes are not displayed. The keyboard comes from @onkeydown. Mouse events are declared but not wired. Files are imported with InputFile and exported through a base64 download. Files live in an in-memory Dictionary with no persistence (no IndexedDB/OPFS). There is no WebAudio.

TESTS. 640 [Fact] plus 3 [Theory] (38 cases), about 678 in total. 323 of them replay the SingleStepTests 8088 v2 suite: hardware-captured JSON (MIT), first 100 cases per opcode, results compared with flag masks. The suite is committed as about 1.25 GB of data. The 32-bit tests (66) are hand-written. No performance measurement exists anywhere.

PROCESS. Roadmap docs: ROADMAP.md (partly out of date), roadmap-ve.md (hardware gaps against the reference BIOS) and src/final-implementation.md (French; Phases 1–2 done, Phases 3–4 open, including 0x67 and protected mode). There is one PR, #1, by the Copilot coding agent: about 20 commits between 2026-02-19 and 02-24, with test counts in the commit messages going 35→56→84→104→120→131→349, and "Address code review" commits in between. After that come manual commits by werddomain, the last on 2026-04-25 (+6.9k lines: FDC, DMA, CMOS, FPU, BIOS Setup).

VERDICT. Worth reusing: the core/platform split, the SingleStepTests-based testing harness, the Copilot agent workflow with phased roadmaps, the yield-and-rewind trick for async waits, and the device models (PIC/PIT/DMA/FDC/CMOS). To be redone: a CPU core with protected mode, paging, exceptions, and probably x86-64; the memory system (TLB, MMIO, more than 1 MB); a bitmap/framebuffer renderer; real-time timing; and async I/O.

Performance (my estimate, not measured): about 100–300 IL operations per guest instruction under the interpreter gives roughly 0.3–2 M instructions/s, maybe 2–10 M/s with AOT. Even the managed loop's own design caps it at about 3.1 M/s. Booting Windows 10 runs about 3e10–1e11 instructions, which works out to hours. The reference emulator v86 (Rust plus an x86→wasm JIT) still has no 64-bit support and does not list Windows 7/10. Windows 7/10/11 x64 is therefore not realistic in C# Blazor WASM. 32-bit Linux or DOS/Win9x is realistic.

## Implications
- Reusable as is or with light changes: the Core/Platform split (headless core library plus host adapters). It fits Kazo OS well: the core in a library, host adapters for the Kazo window, the Kazo VFS and the Kazo network.
- Reusable: the test strategy (SingleStepTests replayed opcode by opcode with flag masks). For a 386+ core, use the 80286/80386 suites (real mode for now) through the OpenRakis NuGet packages instead of committing GBs. Protected mode, paging and x86-64 will need other suites, for example differential tests against QEMU/Bochs or kvm-unit-tests; that is an inference.
- Reusable: the device models (PIC, PIT, DMA, floppy controller, CMOS, speaker) and the yield-and-rewind trick (rewind IP and yield) for async waits in a single-threaded runtime. They will need hardening: real-time timing, edge/level IRQs, APIC/HPET/ACPI for Windows.
- Reusable: the phased Copilot coding agent workflow (PR per phase, test count in commit messages, 'Address code review' commits, French roadmap). Keep the roadmaps in sync with the code, because ROADMAP.md has drifted.
- Must be redone: the CPU core. It needs full decoding with 32-bit ModR/M+SIB, 0x67, descriptor caches, CPL/IOPL, gates/TSS, precise restartable exceptions, a paging MMU with TLB, and V86 mode. For x64 add long mode, REX, RIP-relative addressing, SSE through SSE4.2, POPCNT, CMPXCHG16B, NX, syscall/sysret. The giant switch with immediately computed flags will not scale; prefer table/pre-decoding, lazy flags and a decoded-block cache.
- Must be redone: memory. Guest RAM well beyond 1 MB, MMIO routing (VGA/LFB, APIC, PCI BARs), A20, and probably memory outside the managed heap; a single .NET array is limited to about 2 GB and the browser .NET runtime is wasm32. That last point is my inference and needs checking.
- Must be redone: display and I/O. A framebuffer renderer (VGA/SVGA/VBE, then virtio-gpu or a simple LFB) using ImageData/OffscreenCanvas instead of fillText per cell. Async block I/O (virtio-blk or AHCI with DMA plus IRQ) so it works with Kazo's async storage; the current sync-over-async pattern would deadlock against a truly async VFS.
- Kazo OS integration (shared folder, network): the HLE DosKernel→IStreamProvider pattern shows host file-system mapping at the API level. For Linux, the equivalent would be 9p/virtio-fs to the Kazo VFS, or user-mode syscall emulation. For Windows, a paravirtual driver or an SMB/9p bridge. Network goes through a virtio-net/NE2000 → WebSocket/Kazo relay, since browsers have no raw sockets; that is an inference.
- Performance (estimates, unmeasured): the current C# core probably reaches about 0.3–2 M instructions/s interpreted and 2–10 M/s with AOT. Enough for DOS and maybe Win 3.x/9x and a minimal 32-bit Linux. Not enough for Windows 7/10/11 x64 (tens of billions of instructions to boot, so hours, plus MMU overhead). Getting near usable speed requires a JIT to wasm (v86/CheerpX/qemu-wasm style), which C# cannot do without generating wasm modules and instantiating them through JS. Possible in theory, but no known .NET precedent.
- Delivery size: the AOT .NET runtime plus core is likely several MB, and guest disk images are hundreds of MB to GB. This supports delivering it as a separately downloadable Marketplace module, with images streamed or chunked, as the user wants.
- The test data, the GPL-3.0 8088-PC-Compatible folder and the commercial DOS games should not be copied into Os-x86 (MIT) or Kazo OS (CC BY-NC 4.0). Reference them as external downloads instead.

## Risks
- Very high technical risk on the 'Windows 7/10/11 x64' goal. Even v86, the state of the art with an x86→wasm JIT, does not support 64-bit and only partly supports XP and later. A C# interpreter in Blazor WASM will be far too slow, and Windows 11 24H2 also requires SSE4.2/POPCNT, plus in practice TPM 2.0, Secure Boot and UEFI.
- Guest memory: Windows x64 and modern Linux want 1–4+ GB of RAM. The .NET browser runtime is wasm32 with a heap under 4 GB, and a .NET array is limited to about 2 GB. Allocating guest RAM inside the .NET heap may be impossible or unstable (inference, to verify).
- Single thread: .NET 10 Blazor multithreading is experimental. The CPU emulator will compete with the Kazo OS UI on the same thread unless the emulator runs in its own Web Worker or iframe (separate runtime).
- Sync-over-async: the existing GetAwaiter().GetResult() pattern would throw or deadlock on single-threaded WASM if the provider (Kazo VFS, IndexedDB/OPFS) becomes truly async.
- Throughput is limited by design (fixed batches of 50,000 instructions plus Task.Delay of 16 ms or 1 ms, with browser setTimeout clamping), and timing is instruction-based, so the guest clock drifts from real time.
- The existing correctness base is limited to 8088 real mode (100 cases per opcode). The 32-bit paths (0x66) are only checked by 66 hand-written tests; 0x67 does not exist; there are no exceptions, so guest bugs pass silently, with unknown opcodes run as a NOP.
- Licensing and IP: the test data (MIT) is fine, but the GPL-3.0 code (8088-PC-Compatible) and the commercial games in DOS_Files cannot be redistributed in Os-x86 (MIT) or Kazo OS (CC BY-NC 4.0). Windows images and licenses must be supplied by the user, never shipped.
- Repository size: the MsDos.Clone clone is 2.8 GB because of test data and images. Repeating this in Os-x86 would make CI and Copilot agents slow and expensive.
- Docs drift: ROADMAP.md contradicts the code, and an AI agent following it could reimplement existing features or skip real gaps.
- Version mismatch: MsDos.Clone targets .NET 8 while Kazo OS targets .NET 10, so a migration is needed if any code is reused.

## Open questions
- Which target guests matter first? (A) DOS/Win3.x/9x + 32-bit Linux, achievable; (B) Windows XP/7 32-bit, very hard; (C) Windows 10/11 x64, probably out of reach in the browser. Can we stage it as A, then B, then (C) as research?
- Must the emulator stay in C#/.NET (reusing MsDos.Clone's patterns) even if a v86-type core (Rust/C→wasm with a JIT) would be 10–100x faster? Is integrating or porting an existing open-source core acceptable?
- Should 'run an .exe in Kazo OS' mean booting a full Windows (full-system emulation, like WSL2) or emulating the Windows API in user mode without Windows (Wine/Boxedwine style, like WSL1)? Same question for Linux: full-system with a kernel versus syscall emulation.
- Should Os-x86 reuse MsDos.Clone code directly (same author, .NET 8→10 migration), or only copy its architecture and test strategy into a new 386/x64 core?
- Running model in Kazo OS: may the emulator run in a dedicated Web Worker or iframe with its own .NET runtime (better performance, no UI blocking), or must it run in the same Blazor runtime as the kernel?
- Shared resources: should the 'shared folder' be a paravirtual file system (9p/virtio-fs) needing guest drivers, or a mounted disk image synced with the Kazo VFS? For networking, what does Kazo OS expose (WebSocket relay, server-side proxy, none)?
- Is shipping the Windows 7/10/11 images and licenses the user's responsibility? (Legally they cannot be redistributed in the Marketplace.)
- Should the large test data (SingleStepTests) be pulled through NuGet/CI download rather than committed, unlike MsDos.Clone?
