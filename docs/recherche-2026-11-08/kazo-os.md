# kazo-os

## Summary
Kazo OS (local clone: <scratchpad>/repos/kazo-os, HEAD cd89ee0, version 3.2.1 as of 2026-11-08) is live in wasm2/KazoOs (.NET 10 Blazor WebAssembly, Kazo.Os.sln). src/ is the old TypeScript version. It is read-only and still published at /legacy/ on GitHub Pages. The code is layered: Hosts -> Apps -> SDK (Shared/Kazo.Os.AppSdk*) -> contracts (*.Abstractions) -> Platform (Platform.Core is the kernel: catalog, processes, VFS and mounts, capabilities, sudo, hsh shell, simulated network) -> Infrastructure.Browser (IndexedDB, workers, isolation). OS/Kazo.Os.Ecosystem.Host is the OS packaged as a Razor library. OS/Kazo.Os.Ecosystem is the standalone PWA that ships. Server/Kazo.Os.Server is optional: sync, accounts, HTTP/TCP/UDP relay over WebSocket, grants, pairing, and serving the same WebAssembly OS. It is not a marketplace backend.

App model: a C# [AppManifest] class (AppDefinition). Kinds are Window, Terminal, Service and Web. manifest.json is generated at build. A built-in app is added with one ProjectReference in Kazo.Os.Ecosystem.csproj, and IsSystemApp is set there. Built-in DLLs are lazy-loaded, but the published service worker caches every .dll, .wasm and .js at install, so anything built in costs every user download size.

External apps are .kazoapp zips (manifest, lib/*.dll, wwwroot/). They are installed by kazopkg or the Kazo OS Store from GitHub `kazoos-packages` branches or from the Os-AppMarketPlace catalog (raw.githubusercontent.com). Checks: SHA-256 hashes, a mandatory ECDSA signature for the official catalog, transactions, rollback, and adding without a restart. Limits:
- 64 MiB archive, 128 MiB unpacked, 2000 files.
- Every file is stored in the VFS, where the cap is 16 MiB per file.
- An installed app must be Execution=MainThread.
- An app's own extra assemblies are not packaged yet (issue #419).

An app can ship JS and wasm: wwwroot files are served by the service worker at _content/<Assembly>/ (ADR 0206). `new Worker`, `importScripts` and `instantiateStreaming` all work, and .wasm is served as application/wasm. Apps may inject IJSRuntime. Webamp is the reference pattern: C# window plus a JS module plus a vendored library in wwwroot/lib.

Kernel services an emulator would use:
- **VFS**: a single Unix tree in IndexedDB (256 KiB deduplicated chunks, 16 MiB max file). Writes buffer the whole file and publish it in one atomic write; there is no in-place random write. There are dynamic mounts (hostfs network drives through the File System Access API, Chrome/Edge only). Apps cannot register their own FS provider.
- **Processes**: PIDs in /proc. Commands run in a Web Worker pool, services in dedicated workers, windows on the main thread.
- **IPC**: event bus and shared channels, intents, pipes, KazoConsole.
- **Network**: the simulated network first (kazodns, .hack names). The real network needs the dangerous `network.real.access` capability and a connected server relay. Default relay policy: TCP 80/443, UDP 53/123, at most 4 streams per device, private ranges blocked. KazoClientWebSocket reaches real servers directly, without the server.
- **Other**: canvas windows, WinForms-like styles (None/Tool) and child windows (SDK 3.1), OS fullscreen with keyboard lock, KazoClipboard (text and files), notifications, file-based settings. There is no SDK audio API.

Runtime constraints: cross-origin isolation is on by default (auto plus AuditPassed=true), so SharedArrayBuffer is available, but only in a secure context. There is no AOT, and dynamically loaded assemblies run in the IL interpreter. .NET wasm threads were explicitly rejected by Benoit.

Shell: hsh (a POSIX subset) plus 74 commands rewritten in C#. An executable file is read as text; a NUL byte gives "cannot execute binary file". A shebang can route to an installed command. There is no binfmt, ELF/PE loader or subsystem concept anywhere.

Existing plans:
- Os-App-BoxedWine (GPL-2.0, "Run old Windows programs", Coming) and Os-App-EmulatorJS exist but contain only a LICENSE.
- A "server sandbox" (one Hyper-V VM per user, streamed as H.264) was debated on 2026-10-19 and not started.
- Os-x86 is MIT and contains only a LICENSE.

Licensing: LICENSE.md and LICENSE.txt are both CC BY-NC 4.0 (the Markdown file is a formatted copy; the .txt is the official legal text with its preamble). The SDK NuGet packages ship LICENSE.md.

Conventions: ADRs before code (next free number is 0241), series branches, French-first docs mirrored in English, features.md and change entries on every PR, only Benoit merges into main, questions with choices, and ADR 0135 (no mention of games).

Conclusion: the existing extension points fit a Marketplace app best. A main-thread C# window and commands handle files, network, clipboard and the `.exe` association, while the engine runs in its own JS Web Worker with SharedArrayBuffer. A full Linux/Windows subsystem would also need a few new kernel extension points: a binfmt-style handler for binaries, a large-file or block storage path for disk images, a way to mount the guest file system, and a relay policy suited to guest NAT. Each would be a small ADR in Kazo OS rather than shipping the emulator inside the kernel.

## Implications
- The best fit with existing extension points is a Marketplace app (Os-x86 or Os-App-* built from the Os-AppTemplate kazoos-solution template). A C# Window app on the main thread (plus optional Terminal commands, all MainThread) holds the integration logic. The CPU and device engine runs in its own JS Web Worker, started from the app's wwwroot (ADR 0206), with SharedArrayBuffer and Atomics when the page is isolated (on by default).
- A C# CPU core in the style of MsDos.Clone would run in the Mono IL interpreter (no AOT, no .NET threads, and an installed app cannot run in Kazo's .NET workers). It would very likely be too slow for Linux or Windows guests. A native-compiled wasm engine (C, C++ or Rust via emscripten, such as v86 or BoxedWine) in a JS worker is the realistic path, with C# kept for glue: settings, files, network bridge, UI. This is a performance inference that should be measured.
- Disk images and installation media cannot ride in the .kazoapp: 64 MiB archive and 128 MiB unpacked package caps, 16 MiB per VFS file, and write-whole-file semantics. They need a separate download and storage path: the emulator's own OPFS or IndexedDB, VFS files split into chunks of 16 MiB or less, a hostfs network drive, or a new OS block/large-file API (it would extend issue #379). The design must also decide whether these images are excluded from sync (/home) and from .kosbak backups.
- A shared folder between guest and Kazo OS maps naturally onto the KazoFile API inside the app: a 9p or virtio-fs device for Linux guests, or a mapped drive for Wine-style hosts, under filesystem.user-home.* or private capabilities. Showing the guest file system inside the Kazo OS tree (like \\wsl$) needs a new kernel extension point, because apps cannot register an IFileSystemProvider today.
- Guest networking needs a user-mode NAT (slirp-like) in the emulator that turns guest TCP/UDP flows into KazoTcpClient/KazoUdpClient relay streams (needs network.real.access, admin approval, a connected server, and the default 4-stream, 80/443/53/123 limits), or into KazoClientWebSocket connections to an external relay. The simulated network (.hack sites) can be reached through KazoHttpClient for HTTP only; raw TCP to simulated hosts is blocked until #393 is built.
- Running .exe or ELF from the terminal needs a kernel change: a binfmt_misc-style registration (for example a manifest field mapping magic bytes MZ/ELF or extensions to a handler command) in ShellInterpreter.Scripts.cs, which today rejects binaries. Double-click in File Explorer works now through a FileHandlers declaration (.exe media type) and intents.
- Seamless integration (each guest window as a Kazo window) can build on SDK 3.1 child windows and WindowStyle.None/Tool. Simpler first step: one VM window with canvas, the OS full screen and keyboard lock. Pointer lock and audio are not provided by the SDK, so they belong in the app's JS.
- Shipping the emulator as a built-in kernel app would make every user download its .wasm, because the service worker precaches all assets. The lazy-loading only delays loading into memory. This supports the user's instinct that an external app reduces download size.
- A hybrid fits the project's conventions best: the emulator and subsystems as Marketplace apps, plus a short series of Kazo OS ADRs for generic kernel extension points (binfmt handlers, large-file or block storage, mountable subsystem file systems, possibly packaging an app's own libraries per #419 and auto-resolving app dependencies). Each would follow the ADR-first, French-first docs and features.md rules.
- Windows 7/10/11 x64 inside a pure in-browser emulator is outside what this host can offer: single-threaded .NET, no JIT for guest code inside Kazo, and memory and storage limits. The project's own 'server sandbox' idea (Hyper-V VM per user, streamed) is the existing design direction for modern Windows; the browser emulator could target 32-bit guests (Linux i686, older Windows) first.

## Risks
- Performance: the interpreted .NET runtime (no AOT; dynamically loaded assemblies cannot be AOT-compiled) and the rejection of .NET wasm threads make a C# emulator core impractical. A JS or wasm engine is needed, which goes against the AGENTS.md preference for C# unless justified as 'impractical in C#'.
- Installed apps run only on the main thread. A synchronous emulation loop in the app's C# would freeze the whole OS desktop and trigger 'Not responding'. All heavy work must live in the app's own JS Web Worker, which is outside Kazo's process and CPU/memory accounting.
- Storage: 16 MiB max file size, IndexedDB quota and eviction, and no random-access write in the VFS. Multi-GB Windows images are unrealistic in the VFS. Even a Linux image needs a dedicated storage strategy, and sync and backup could balloon if images live under /home.
- Packaging: 64/128 MiB and 2000-file package limits. An app's extra assemblies are not packaged (#419). The trimmed-runtime API check can refuse an emulator using framework APIs absent from the trimmed OS. Package dependencies do not appear to be auto-resolved (medium confidence).
- Networking depends on the optional server and on dangerous-capability approval. Default quotas (4 streams per device, TCP 80/443 only, UDP 53/123, no private networks, no port ranges in RealNetworkPorts) would break normal guest OS traffic unless an admin relaxes the policy or an alternative relay is used.
- Cross-origin isolation (needed for SharedArrayBuffer) depends on the service worker and a secure context. It is absent on localhost/127.0.0.1 dev hosts and in browsers without a service worker. COEP credentialless also blocks reading cross-origin resources without CORS (for example, GitHub Release downloads of disk images).
- Licensing: the Kazo OS SDK packages are CC BY-NC 4.0 while Os-x86 is MIT. Wrapping GPL engines (BoxedWine GPL-2.0, QEMU GPL-2.0) would require the app repo to be GPL (the project's own rule), and GPL's no-additional-restrictions clause may conflict with distributing a combined package that links a NonCommercial-licensed SDK. This needs legal review; it is not legal advice.
- Guest OS licensing: Windows images cannot be redistributed. Users must supply their own media and licenses, which affects the UX and the Store review.
- Overlap and governance: Os-App-BoxedWine is already planned, and the 'server sandbox' (Hyper-V) idea exists in the maintainer's decisions. A new Os-x86 effort must be reconciled with them, and its kernel-side changes must go through ADRs (next free 0241) before code.
- ADR 0135 sensitivity: emulators are often presented for games. Kazo OS docs and ADRs must avoid any mention of games (exception: features.md for ported apps).
- Browser coverage: hostfs network drives and some screen features are Chrome/Edge only, and keyboard lock needs full screen. Firefox, Safari and mobile would get a degraded experience.

## Open questions
- Should Os-x86 replace, absorb or coexist with the already planned Os-App-BoxedWine (GPL-2.0) and the 'server sandbox' (Hyper-V VM per user) idea for running real Windows apps?
- Delivery: a pure Marketplace app, a built-in kernel feature, or a hybrid (Marketplace emulator plus small generic Kazo OS kernel extension points such as binfmt handlers, large-file storage and subsystem mounts)?
- Engine choice: write a new C# core (reproducing MsDos.Clone) despite interpreted .NET, or wrap an existing wasm engine (v86 for 32-bit x86, BoxedWine for Win32 apps, or another) with C# glue?
- Licence of Os-x86: keep MIT (compatible with BSD engines such as v86) or switch to GPL to wrap GPL engines? How should the CC BY-NC 4.0 licence of the Kazo OS SDK packages be handled?
- Target guests and priority: 32-bit Linux (which distribution), older 32-bit Windows, Win32 apps only (Wine-style), or x64 Windows 7/10/11? Is 32-bit acceptable as phase 1?
- Where should disk images live (emulator-owned OPFS or IndexedDB, chunked VFS files, host-folder network drive, or a new OS block-storage API), and must they be excluded from /home sync and system backups?
- Networking: is relying on the optional Kazo OS server relay (with its quotas and admin approval) acceptable, or should the emulator use its own WebSocket relay? Should guests also reach the simulated network (.hack sites) and listen on simulated ports?
- Integration depth: one VM window, or seamless guest windows mapped to Kazo child windows? Should '.exe' double-click and a terminal command (wsl-like or wine-like, binfmt) be in scope for v1?
- Who can install and use it: a per-user install from a trusted source, or system-wide only by an administrator? Which dangerous capabilities (network.real.access, filesystem.user-home.write) are acceptable to request?
