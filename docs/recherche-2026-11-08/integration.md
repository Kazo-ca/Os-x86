# integration

## Summary
Research covered host integration for a browser x86/x64 emulator running inside Kazo OS (Blazor WASM .NET 10). Kazo already has most of the host-side infrastructure, and that changes the design. It sets COOP same-origin plus COEP credentialless through its service worker, with a require-corp fallback for Safari. This is on by default since the audit passed (2026-10-18). It already uses 1 MiB SharedArrayBuffer SPSC rings and Atomics.wait in workers, and explicitly does not use .NET WASM threads. Installed Hack Store apps can ship a JS/wasm engine that runs in a Web Worker, served under _content/<assembly>/ (ADR 0206). Kazo also has a clipboard owned by the OS with a host bridge, File System Access host folders mounted as /mnt network drives, and an SDK network gateway (KazoDns, KazoHttpClient, KazoHttpListener, KazoTcpClient/KazoUdpClient). The emulator should therefore be a worker-hosted JS/wasm engine plus a thin 'Kazo host bridge'. It should not be a C# CPU loop that pushes frames through IJSRuntime, which is the MsDos.Clone pattern.

Shared folder. For Linux guests, virtio-9p is the natural path. v86 supports it (tag host9p, handle9p custom server hook) and so does QEMU-wasm (virtfs from the Emscripten FS). For Windows guests no virtio-9p client exists. The options are: (a) virtio-fs, which needs virtio-win viofs plus WinFsp in the guest, works on Win8+/10/11 but not Win7, and requires us to implement the vhost-user-fs device inside the emulator because there is no virtiofsd in a browser; (b) the built-in SMB client against a C# SMB server (SMBLibrary, LGPL) reached over the emulated network, where Win11 24H2 now requires signing and blocks guest logons on Pro; (c) WebDAV, which is deprecated since Nov 2023; (d) VMware HGFS over the backdoor, which v86 already partly implements (absolute mouse, text clipboard, time); (e) a custom Kazo guest agent; (f) ISO/FAT image injection as a universal one-shot fallback (v86 has a built-in Joliet ISO generator).

Network. Browsers have no raw sockets. Options are a raw-frame WebSocket relay (websockproxy), Wisp v2.1 (TCP/UDP multiplexed over one WebSocket, used by v86), fetch-only HTTP (CORS-limited), or Tailscale/WireGuard over DERP WebSockets (WebVM; about 16 MB of wasm). The recommended bridge is a user-space TCP/IP stack in the emulator worker: v86 fake_network or lwIP-wasm tcpip.js (MIT, under 100 KB). It terminates guest TCP/UDP and maps each flow onto Kazo's gateway. Simulated hosts are HTTP-level only today (TCP to a simulated host is issue #393). Real hosts go through the optional server relay, which uses one WebSocket per TCP stream with default ports 80/443, UDP 53/123, and MaxStreamsPerDevice=4. Kazo's own rule says no feature may depend on the server, so we need a fetch-only offline fallback and probably a Wisp-style multiplexed endpoint.

Display, input, audio, clipboard. The framebuffer should live in a SharedArrayBuffer and be drawn on an OffscreenCanvas in the worker; Safari only got WebGL there in 17. Guest drivers differ by OS:
- Display: Bochs VBE / std VGA gives Windows 8+ 'Basic Display Adapter'. virtio-gpu needs viogpudo with a limited set of resolutions.
- Absolute pointer: USB tablet uses Windows' inbox HID driver; virtio-tablet needs vioinput; the VMware backdoor needs vmmouse.
- Audio: SB16 serves Win9x/XP and HDA serves Win7+/Linux (there is no 64-bit AC97 driver). Output goes through AudioWorklet with a SharedArrayBuffer ring.
- Clipboard: guest side via the VMware backdoor, vdagent on a virtio-serial port, or a Kazo agent, mapped to Kazo's SystemClipboard.

Storage. Base images are streamed lazily over HTTP Range requests or as chunked parts (v86 use_parts). Guest writes go to an OPFS copy-on-write overlay through SyncAccessHandle in the worker. Note that v86 keeps writes only in RAM and in save states. Quotas are per origin and shared with Kazo's IndexedDB file system. Chrome allows 60% of disk. Firefox best-effort allows the smaller of 10% of disk and 10 GiB (persistent: 50% of disk, up to 8 TiB). Eviction removes the whole origin unless persist() is granted.

Sizes:
- v86.wasm: 2.0 MB (about 280 KB gzip).
- QEMU-wasm x86_64 demo: 40.8 MB (14.6 MB gzip).
- SeaBIOS: 128-256 KiB.
- OVMF: about 2.2-2.4 MB bz2 (the Secure Boot build needs SMM).

x64 and Windows 10/11 require a QEMU-class core, since v86 has no 64-bit or SMP support. QEMU-wasm's wasm32 build is capped at about 2.3 GB in the demo, and the wasm64 TCG backend was still unmerged as of v5 in Jan 2026. Memory64 is not available in Safari. Win11 also needs UEFI + Secure Boot + TPM 2.0, at least 4 GB RAM, at least 64 GB disk, and POPCNT/SSE4.2.

## Implications
- Run the emulator core (JS/wasm: v86 for 32-bit, a QEMU-wasm-class core for x64) in its own dedicated Web Worker, separate from the Kazo .NET worker pool. Blazor/C# only drives the control plane (start/stop, config, snapshots) through JSImport/JSExport. Frames, audio and disk I/O never cross IJSRuntime; the MsDos.Clone per-frame InvokeVoidAsync pattern does not scale to SVGA.
- Reuse Kazo's existing cross-origin isolation (COOP + COEP credentialless, auto=on) and its sharedRing.js design. Use SharedArrayBuffer for the framebuffer, an audio ring buffer, and NIC/9p rings between the emulator worker and a JS 'Kazo host bridge'. The main thread never waits (Atomics.wait only in workers). Do not rely on .NET WASM threads (experimental in .NET 10, unsupported by Blazor).
- Shipping as a Hack Store/Marketplace app is technically supported today (ADR 0206: wwwroot engine plus worker plus wasm served by the service worker with COOP/COEP). The emulator wasm (v86 about 2 MB / 280 KB gzip; QEMU-wasm about 41 MB / 15 MB gzip) fits that path. Firmware, ISOs and disk images should be downloaded on demand into OPFS, not packaged as app assets in IndexedDB. Kernel integration is not needed for bridging, because the SDK gateways already exist. The engine app needs grants such as network.real.access, filesystem.system.*, and clipboard.read/write.
- Shared folder, Linux guests: implement a 9P2000.L server over the Kazo VFS (v86 handle9p hook, or QEMU virtfs backed by a custom FS). Guests mount it with mount -t 9p host9p. Map Kazo users and permissions to fixed uid/gid and modes, and invalidate caches when Kazo files change.
- Shared folder, Windows guests: 9p is not an option. Per-version choice: Win 8/10/11 can use a virtio-fs device implemented in the emulator (FUSE-over-virtqueue) plus virtio-win viofs and WinFsp in the guest. Win 7, or 'no driver install', can use the inbox SMB client against a C# SMB server (e.g. SMBLibrary) listening on a virtual gateway IP inside the user-space network; it must support NTLM auth and signing for Win11 24H2 and SMB1 for XP. Win9x/2000/XP on v86 can use VMware-backdoor HGFS or a Kazo guest agent. Universal read-only fallback: inject files as ISO/FAT images.
- Network: put a user-space TCP/IP layer in the emulator worker (v86 fake_network or lwIP-wasm tcpip.js) that terminates guest flows and calls a Kazo socket gateway. Routing: DNS goes to kazodns; HTTP to simulated hosts goes to AppNetworkGateway/KazoHttpClient/KazoHttpListener; other TCP/UDP to real hosts goes to KazoTcpClient/KazoUdpClient via the server relay. Without the server, fall back to fetch-only HTTP, which is CORS-limited.
- Kazo's relay opens one WebSocket per TCP stream with MaxStreamsPerDevice=4 and default ports 80/443. A guest OS (browser, apt, Windows Update, SMB) will exceed this immediately. We need either a multiplexed Wisp-style endpoint in Kazo.Os.Server (spec CC-BY, simple to port to C#) or a VM-specific relay policy and quota.
- Make guests visible on Kazo's simulated LAN: give each VM an IP in the simulated network so ping/nmap/curl can see it, and forward guest listening ports into ListeningPortTable (v86 fetch backend already has a guest-listener API). VM-to-VM traffic can use a BroadcastChannel or tcpip.js bridge. Raw TCP to simulated hosts depends on Kazo issue #393.
- Display: draw from a SharedArrayBuffer framebuffer onto an OffscreenCanvas transferred from the Kazo window's <canvas> to the emulator worker. Bochs VBE / std VGA is the baseline (Windows 8+ Basic Display Adapter, VBEMP for NT/2000). Dynamic resizing needs virtio-gpu (viogpudo on Windows, virtio-gpu DRM on Linux) or VMware SVGA.
- Input: PS/2 as the baseline. For absolute pointing, use USB tablet (Windows inbox HID, no driver), the VMware backdoor (already in v86; vmmouse drivers) or virtio-tablet (Linux inbox, vioinput on Windows). Pointer lock for relative and game mode. Keyboard Lock in fullscreen for Win key and Alt+Tab, Chromium only. Kazo must not intercept guest shortcuts while the VM has focus.
- Audio: SB16 for Win9x/2000/XP, Intel HDA for Win7+ and Linux (avoid AC97 on 64-bit Windows). Output through AudioWorklet fed by a SharedArrayBuffer ring from the emulator worker, ideally routed through Kazo's volume and sound settings.
- Clipboard: add a VM origin to Kazo's SystemClipboard. Guest-side transports: VMware backdoor text commands (v86), vdagent protocol on a virtio-serial port named com.redhat.spice.0 (spice-vdagent on Linux and Windows; v86's virtio-console port names need patching), or a Kazo guest agent. Host export still goes through HostClipboardBridge.
- Storage: read-only base images are streamed lazily (HTTP Range, or pre-split chunks for static hosts or the service worker). A copy-on-write overlay lives in OPFS through SyncAccessHandle in the emulator worker, exposed to v86 as a custom get/set/load buffer. Snapshots (non-zero RAM pages plus dirty blocks, zstd) also go to OPFS. Request navigator.storage.persist() and show VM disk usage in Kazo df/Diagnostics, because it shares the quota with Kazo's IndexedDB disk.
- Optionally do the reverse direction: expose guest disks or guest shares to Kazo as mounts through IDynamicFileSystemMountRouter (as with ADR 0181 network drives), so the Kazo file explorer can browse VM files.
- Linux vs Windows: Linux guests have inbox drivers for virtio-net/blk/9p/input/gpu, vmmouse and HDA, so they get full integration with no extra installs. Windows guests need virtio-win (Win8+), WinFsp, spice-guest-tools or qemu-ga, or VMware Tools. Otherwise only inbox paths work (e1000/rtl8139 NIC, AHCI/IDE, USB tablet, HDA, SMB client, Basic Display Adapter). A per-Windows-version compatibility matrix and a 'Kazo Guest Tools' ISO are required.

## Risks
- x64 Windows 10/11 performance under browser TCG is unknown and likely very slow. No benchmarks were found, and the QEMU-wasm wasm64 TCG backend was still an unmerged patch series (v5, Jan 2026).
- Memory: wasm32 caps linear memory at 4 GB and the QEMU-wasm demo uses 2300 MB, while Win11 needs at least 4 GB RAM. Memory64 is Chrome/Firefox only (no Safari), slower, and increases code size.
- Windows 11 also requires UEFI Secure Boot (OVMF secure build requires SMM emulation), TPM 2.0 (would need a TPM emulator in-browser), at least 64 GB disk, and POPCNT/SSE4.2 for 24H2. Each one is a hard blocker if missing.
- Licensing: Os-x86 is MIT, but QEMU is GPLv2, Boxedwine GPL-2, SMBLibrary LGPL-3, wisp-js LGPL-3, open-vm-tools LGPL-2.1, and CheerpX is proprietary (commercial license for organizations). Linking choices can force license changes or a separate distribution. Redistribution terms for virtio-win/WinFsp guest binaries and Windows install media are unverified.
- Kazo relay limits (MaxStreamsPerDevice=4, ports 80/443, UDP 53/123) and the 'no feature may depend on the server' rule mean guest networking is either severely limited or needs new server work (multiplexing, per-VM policy). Opening the relay wider increases SSRF and abuse exposure.
- Windows shared folders: there is no 9p client. virtio-fs is not supported on Win7, has reported WinFsp-launcher problems on Win10, and fails some WinFsp tests. SMB on Win11 24H2 requires signing and blocks guest logons on Pro, so the SMB server needs a full auth and signing implementation. WebDAV is deprecated and disabled by default.
- Storage eviction is per whole origin: if the browser evicts best-effort storage, VM disks and the entire Kazo OS IndexedDB file system go together. Firefox best-effort caps at 10 GiB, so multi-GB Windows disks need persist() to be granted.
- v86 async disks keep guest writes only in RAM and in save states. Without a custom OPFS overlay, writes are lost on reload. Range requests also disable HTTP compression.
- Safari gaps: no COEP credentialless (Kazo falls back to require-corp, which blocks non-CORP third-party resources), no Memory64, no File System Access directory picker, no Keyboard Lock, and OffscreenCanvas WebGL only since 17 with bugs.
- Clipboard export from guest to the real host needs a user activation for navigator.clipboard.writeText. Guest-originated copies arrive asynchronously and may miss the transient activation window. Unverified.
- v86 virtio-console uses fixed port names (virtio-N), so the standard spice-vdagent and qemu-ga channels do not work without patching the emulator.
- Windows inbox NIC support for e1000/rtl8139 on Win10/11 is based on anecdotal reports; e1000e has had driver issues on Win10. virtio-net needs NetKVM. This must be validated per build.
- QEMU-wasm demos are console-only. A graphical display backend (framebuffer to canvas) for QEMU in the browser would have to be written; none was documented.
- Each extra .NET worker costs 15-40 MB and 0.5-2 s, and Blazor's main thread must never block. A C#-side emulator loop (MsDos.Clone style) would compete with the Kazo UI.

## Open questions
- Priority guests: Linux (32-bit via v86 now) first, or Windows first? Which Windows versions are must-have (9x/XP on 32-bit, 7, 10, 11), given that x64 and Win11 bring the memory, UEFI, TPM and performance blockers?
- Should guest real-network access require the optional Kazo server (relay/Wisp), or must VMs work with no server at all, accepting fetch-only HTTP and simulated hosts?
- Should VMs appear as hosts on Kazo's simulated network (pingable, nmap-able, reachable by Kazo apps, able to browse simulated sites like hackersearch.net), or be isolated?
- Shared-folder scope: which Kazo paths are exposed (home only, a chosen folder, /mnt network drives), read-only or read-write, and how Kazo users and permissions map to guest users?
- Is it acceptable to require installing guest drivers/tools inside Windows (virtio-win, WinFsp, a 'Kazo Guest Tools' ISO), or must integration work out of the box (SMB, USB tablet, e1000, HDA only)?
- Where should VM disks live: OPFS outside the Kazo VFS (fast, invisible to the file explorer and backup), or as files inside the Kazo VFS? What storage budget per VM is acceptable?
- Licensing: may Os-x86 (MIT) include or link GPL/LGPL components (QEMU, SMBLibrary, wisp-js), or must it stay permissive (which would favor v86 plus custom code)? How does that interact with Kazo OS's CC BY-NC 4.0?
- Target browsers: Chromium-only (Memory64, Keyboard Lock, File System Access, credentialless), or must Firefox and Safari also run VMs?
- OS images: will users bring their own Windows ISOs and licenses, while Kazo only hosts free Linux images? Are prebuilt snapshots (save states) acceptable for fast boot?
- Clipboard scope: text only, or also images and files (drag-and-drop of Kazo files into the guest)?
- Delivery: should the emulator engine ship as one Marketplace app per core (v86-32 and x64), or one app with downloadable cores and firmware?
